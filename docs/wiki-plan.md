# 위키 다음 작업 — 무엇을 알고 시작하는가

2026-09-02에 위키 축을 네 번 쟀고, 그 결과가 다음 작업의 우선순위를 뒤집었다.
수치는 `docs/eval/2026-09-02-*`에 있다. 이 문서는 **그것들이 합쳐서 말하는 것과
실행 계획**만 적는다.

**이 문서에는 골든셋의 질문도 정답도 적지 않는다.** `.md`는 색인되고 섹션 노드까지
생기므로, 여기 적힌 문장은 그대로 측정 대상의 검색 결과가 된다.

## 1. 확립된 것 넷

1. **주입은 정답률이 아니라 비용을 바꾼다.** 위키가 답을 갖는 6문항에서 정답
   17/18 → 18/18(판정 아님)인데 입력 토큰은 303K → 19K, 문항별 10.7~25.2배로
   6/6 같은 방향(p=0.031). [wiki-injection](eval/2026-09-02-wiki-injection/findings.md)
2. **값은 지식의 존재가 아니라 도달 비용이다.** 주입 없는 팔 18런 중 9런이
   `docs/wiki`를 스스로 찾아 읽고도 10~25배를 썼다. 주입이 없애는 것은 지식의
   부재가 아니라 찾는 수고다.
3. **에이전트가 필터로 작동한다.** 게이트를 켜고 위키 도구만 쥐여준 팔이 러너가
   전부 주입한 팔과 **같은 정답률(13/18)을 절반 토큰(316K 대 575K)으로** 냈다.
   카탈로그가 빈 9런은 전부 빈 `wiki_resolve`로 나갔고, 카탈로그가 있는 9런은
   하나도 빈 호출을 하지 않았다. **억지 주입 0건.**
   [combined §재측정](eval/2026-09-02-combined/findings.md)
4. **그러므로 preflight의 병목은 정밀도가 아니라 재현율이다.** 에이전트가 여분을
   걸러내므로, 카탈로그가 넉넉한 것보다 **비는 것이 더 비싸다.** 실제로 오매칭
   하나를 제거한 수정이 그 문항의 카탈로그를 비게 만들어 게이트 팔을 1/3 → 0/3으로
   떨어뜨렸다.

## 2. 확립되지 않은 것 셋

- **교차 언어.** 세트 라벨은 한국어이고 영어 질의는 닿지 않는다. 같은 여섯 질문을
  한국어로 던지면 정답 세트를 5/5 재현하는데, 영어로는 4문항 중 하나도 정확히
  고르지 못한다. `preflight`는 라벨만 보므로 구조적이다. → **P1로 닫았다**(같은 날,
  §4 P1 결과).
- **서브에이전트 경로의 압력.** 게이트 메시지 셋 중 그 경로에만 "빈 카탈로그로도
  통과한다"는 안내가 빠져 있었고 채웠다. 측정은 메인 세션(default 경로)에서만
  했으므로 수정한 경로의 답은 아직 없다.
- **에이전트가 만든 세트의 품질.** 그 경로가 아직 없다. → 유지보수 경로는 P2로
  열렸고 첫 드릴은 통과했다(§4 P2 결과). **생성** 경로는 여전히 없다.

## 3. 함정 — 반드시 먼저 읽을 것

이 세션이 실제로 밟은 것들이다. 다시 밟으면 결과가 조용히 틀린다.

| 함정 | 무엇이 일어나나 |
|---|---|
| `go build ./...`는 `bin/graphin`에 쓰지 않는다 | **`make build`를 써야 한다.** 4시간 전 바이너리로 런을 돌려 수정 전 결과를 얻었다 |
| 골든셋 질의 파일의 `top_k`가 `--top-k`를 덮는다 | `eval-recall.py:123`. 스윕하려면 `--queries`로 사본을 넘긴다 |
| grep 대조군을 층 합계로 비교하면 분모가 다르다 | "심볼 추측"은 추측 가능한 문항만 센다. 문항 수를 맞춰야 한다 |
| 부호검정을 `2·(1/2)^n`으로 쓰면 검정이 아니라 상수다 | 관측과 무관하게 같은 값이 나온다. 실제 이항검정을 써야 한다 |
| `evidence_any`는 `\|` 대안을 split하지 않는다 | `evidence`만 한다. 리스트 자체가 대안이다 |
| 봉쇄 훅 없이 grep 팔을 돌리면 플러그인 캐시의 저장소 사본을 읽는다 | 같은 문항 입력 토큰이 148K → 52K로 떨어졌다. 이전 값은 코퍼스 밖 |
| 세트를 늘리면 preflight 매칭이 바뀐다 | **이 문서를 쓰면서 즉시 밟았다.** 일곱 번째 세트를 더하자 여분이 3에서 8로 튀었다 — 공통 키 문턱이 올림(`(n+1)/2`)이라 세트 하나에 1이 올라가고 걸러지던 키가 한꺼번에 되돌아왔다. 내림으로 고쳤고(6·7세트가 같은 문턱 3), 지금 여분은 2다. **비슷한 규칙을 더할 때 같은 함정을 본다** |
| `docs/wiki/sets/*.md`는 색인된다 | 세트가 늘면 검색 결과에 세트 파일이 뜬다. 지금 규모에서는 무시할 만하다 |

## 4. 개선 방안 — 세 단계

순서에 근거가 있다. **P1은 값싸고 측정 장치가 이미 있으며, P2는 위험이 낮고,
P3은 P2의 관측 없이는 판단할 수 없다.**

### P1 — 교차 언어 재현율

**문제.** §2가 적은 그대로다. 그리고 §1.4가 이것을 우선으로 만든다 — 빈 카탈로그가
가장 비싼 실패인데, 교차 언어가 빈 카탈로그의 주 원인이다.

**후보 둘.**

- **ⓐ 세트 frontmatter에 별칭.** `aliases: [release, versioning, gate tier]`처럼
  다른 언어·어휘의 라벨을 손으로 적는다. `matchesTask`가 이름 직격 경로에서 읽으면
  된다. 값싸지만 손으로 유지해야 하고, 세트가 늘면 부담이 는다.
- **ⓑ 매칭에 의미 신호를 넣는다.** 세트 요약을 임베딩해 질의와 비교한다. 유지
  부담이 없는 대신 인덱스가 준비돼야 하고(`semantic_ready`), preflight가
  인덱스 없이 도는 지금 성질을 잃는다 — `graphin wiki`의 모든 verb가 인덱스 없이
  도는 이유가 있다(`console-spec.md §3`).

**권고: ⓐ부터.** ⓑ는 preflight의 기동 조건을 바꾸므로 별도 결정이다.

**검증.** `internal/wiki/preflight_real_test.go`가 한국어 여섯 질의의 재현율과
여분을 이미 고정한다. **영어 질의 케이스를 같은 표에 추가**하고, 재현율이 오르는지
여분이 얼마나 느는지 본다. 여분 상한은 §1.4에 따라 **느슨하게** 잡는다.

**결과 (2026-09-02, ⓐ 구현).** 일곱 세트에 `aliases:`를 적고 이름 직격 경로에서
읽게 했다. 영어 열두 질의에서 정답 세트 재현 5/11 → **11/11**, 빈 카탈로그로
끝난 커버 문항 4 → **0**, 여분 총계 5 → 5. 한국어 여섯 질의는 2 → 2로 그대로다.
부수 수정 둘: 라틴 낱말도 인덱스처럼 어간을 키에 넣는다("releasing"이 `release`를
만난다), 영어 폐쇄류 낱말을 문법어 stop에 더한다(라벨의 "Do's and Don'ts"가
영어 질의마다 `design`을 끌어오던 것). 별칭은 토큰 서명 범위에 들어간다.

### P2 — 세트 유지보수를 에이전트에게

**왜 생성보다 먼저인가.** 결정 큐 여덟 종 중 셋은 **새 주장을 만들지 않는다.**

| 종류 | 필요한 능력 | 새 주장? |
|---|---|---|
| `dangling` — 엔트리의 노드가 사라짐 | 탐색(새 노드 찾기) | 아니오 |
| `drift` — 핀은 됐는데 내용이 바뀜 | 읽고 요약 다시 쓰기 | 아니오 |
| `unread_set` — 카탈로그에 뜨는데 안 열림 | description 다시 쓰기 | 아니오 |
| `uncovered` — 답이 없던 작업 | **새 세트를 쓴다** | **예** |

앞의 셋은 에이전트가 가장 잘하는 일(탐색과 요약)이면서 위험이 낮다. 그리고
`EditSetFront`가 이미 `description`·`roles`를 고칠 수 있게 해두었는데 호출자가
콘솔 하나뿐이다.

**구현 지점.**

1. **쓰기 도구.** 지금 세트를 고치려면 markdown을 손으로 편집하는 수밖에 없고,
   그러면 앵커 오류·형식 오류가 그대로 들어간다. 용어 경로가 패턴을 확립해 두었다 —
   `wiki_propose`는 *"용어집에 직접 쓰지 않는다. 제안을 접수하고 기계 판정을
   돌려준다."* 최소한 **앵커 실재·중복 여부를 반환하는 도구**가 필요하다.
2. **`Judge`의 세트 버전.** 용어의 세 규칙에 대응하는 것: 앵커가 실재하는가 ·
   기존 세트와 중복인가 · **인덱스가 이미 답하는가**(패키지 doc의 경계:
   "인덱스가 풀 수 있는 것은 위키 지식이 아니다"). 기계가 판정할 수 있는 것만
   게이트로 삼고 나머지는 표시로 남긴다.
3. **표시.** 사용자 결정은 "즉시 반영 + 사후 통제"다. frontmatter에
   `origin: agent` / `reviewed: false`를 두고 `wiki_resolve`가 함께 서빙한다.
   자리는 이미 있다 — drift 표기가 같은 패턴이고 이유도 적혀 있다:
   *"답을 거부하는 세트가 캐비앗과 함께 답하는 세트보다 나쁘다."*
   결정 큐에 `unreviewed` 종류를 더하면 사람의 사후 통제가 무엇을 볼지 알게 된다.
4. **게이트 등재.** 새 서브에이전트는 `docs/wiki/agents.md`에 줄이 있어야 한다.
   **표에 없으면 `AgentGated`이고 면제가 아니다**(`AgentTable.Role`).

**검증.** `scripts/eval-wiki.py`에 팔을 하나 더한다 — 같은 질문에 **사람이 만든
세트**와 **에이전트가 만든 세트**를 각각 주입해 비교한다. 러너는 이미 그 모양이다.

**결과 (2026-09-02, 구현).** 네 지점을 다 넣었다. ① `wiki_edit_set`(repoint ·
summarize · confirm · describe) — 인덱스 없이 돌고, 한 엔트리의 줄만 바꾸며, 앵커
실재·문서 여부·같은 세트 내 중복·빈 요약을 기계 판정한다. ② 그 판정이 `JudgeEntry`,
용어의 `Judge`와 같은 `Verdict`를 돌려준다. ③ 표시는 frontmatter `reviewed: false`
(+ P3용 `origin`)이고 preflight 카탈로그·resolve의 모든 절·`wiki queue`·콘솔 결정 큐
(`unreviewed`, drift 다음)가 함께 낸다. 사람은 `reviewed: true`로 끝낸다. ④
`wiki-maintainer`를 내장 표와 `agents.md`에 exempt로 올렸다 — 위키를 **고치는**
에이전트라 지식 게이트가 막으면 안 된다. 검증은 계획과 달리 **결정론 드릴**을 먼저
돌렸다: 부순 여섯 항목 6/6 처리, 정답 있는 셋 전부 정답, 부수 피해 0
([wiki-maintain](eval/2026-09-02-wiki-maintain/findings.md)). 주입 비교 팔은
`eval-wiki.py --agent-wiki`로 만들어 두었으나 앵커가 전부 원래대로 돌아와 두 팔의
프롬프트가 같으므로 돌리지 않았다. 헤딩을 실제로 고쳐 쓴 어려운 모드는 5/6 — 오답
하나는 상위 절 대신 핵심 주장이 사는 하위 절로 옮긴 것이고, 비용은 1.6배다.

### P3 — 세트 생성 위임

P2의 관측 없이는 판단할 수 없다. 전제 셋:

- **트리거는 마찰 로그다.** "컨텍스트에서 추출"만 하면 매 작업마다 세트가 생긴다.
  `FrictionMiss`가 *"이 작업이 지식을 원했는데 못 받았다"*를 이미 기록하고, 주석이
  생성 원칙을 못 박는다: *"위키는 지식을 원했는데 못 받은 작업에서 자라야 하고,
  문서를 사후에 훑어서 자라면 안 된다."*
- **상한이 필요하다.** 용어집에는 `GlossaryCap = 30`이 있고 이유가 명시적이다.
  세트에는 없다. 그리고 세트가 늘면 §3의 마지막 두 함정이 함께 커진다.
- **시점은 작업 마무리다.** 엔트리 요약은 *"무엇에 관한 것인지가 아니라 무엇을
  주장하는지"*를 적어야 하고, 그건 그 절을 실제로 읽고 쓴 에이전트만 안다.

**결과 (2026-09-03, 구현).** 전제 셋을 전부 기계 규칙으로 옮겼다. `wiki_write_set`은
세트를 통째로 받고 `task`(preflight에 준 문장 그대로)를 요구하며, ① 그 작업의
`coverage_miss`가 마찰 로그에 없으면 거절하고(`unasked` — 트리거는 로그다),
② 세트를 넣은 상태로 같은 작업을 매칭해 안 뜨면 거절하고(`unreachable` — 세트가
그 miss를 실제로 닫아야 한다), ③ `SetCap = 30`을 넘으면 거절한다. 나머지 규칙은
엔트리 편집과 같다(앵커·문서 여부·중복·빈 요약, 그리고 기존 세트의 부분집합).
roles는 받지 않는다 — 푸시는 저자의 상시 결정이라 한 작업 끝에서 정할 것이
아니다. 쓴 세트는 `origin: agent` + `reviewed: false`로 즉시 서빙되고 P2의 사후
통제를 그대로 탄다. 첫 드릴(사람 세트 `rag-bench`를 지우고 그 문항으로 miss를
낸 뒤 마무리에 쓰게 함): 거절 0회로 첫 시도에 통과, 다시 preflight하면 그 세트가
뜬다, 답도 정답. 사람 세트 13엔트리 대 에이전트 5엔트리 — 작업이 물은 축만
깊게 썼다([wiki-author](eval/2026-09-03-wiki-author/findings.md)). 계획서가 적은
주입 비교(3팔 × 3런): **사람 세트와 에이전트 세트가 정답 3/3, 19K 토큰, 툴콜 0으로
같다**, 주입 없음은 495K. resolve 예산이 사람 세트를 자르므로 좁게 쓴 세트가 손해가
아니다. 한 문항의 결론이고, 반례가 나올 자리는 문항 교차다.

## 5. 측정 장치 넷 — 무엇을 언제 쓰나

| 장치 | 재는 것 | 명령 |
|---|---|---|
| `scripts/eval-recall.py` | 검색 한 콜의 recall@k · delivery · 바이트 | `--tier all [--semantic]` |
| `scripts/eval-rag.py` | 에이전트 루프의 행동. **릴리스 게이트가 이것이다** | `run --out … --runs 3` |
| `scripts/eval-wiki.py` | 주입 효용(주입 없음 / 있음 2팔) | `run --out … --runs 3 --jobs 2` |
| `scripts/eval-combined.py` | 통합 3팔(grep / 러너 주입 / 게이트) | `run --out … --runs 3 --jobs 2` |

- 넷 다 **`make build`가 먼저다**(§3).
- `eval-combined.py`는 `--arms`로 팔을 고를 수 있다.
- 긴 런은 `nohup setsid`로 분리한다. 러너는 완주해야 `summary.json`을 남기고,
  채점기는 그 표식이 없는 디렉터리를 거부한다.
- `eval/rag`와 `eval/rag/rubric.lock`은 **소유자 승인 없이 고치지 않는다.**
  `eval/wiki`·`eval/combined`·`eval/golden/tests`는 이 세션이 새로 만든 것이라
  락에 없다.
