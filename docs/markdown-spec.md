# 마크다운 그래프 스펙 — 섹션을 원자로 (v1)

마크다운을 헤딩 단위로 쪼개 **섹션을 그래프의 원자**로 만든다. 파일 탐색은
지금 잘 되므로 그대로 두고, 무너져 있는 **내용 검색과 정확한 추출**을 고친다.

**상태 (2026-08-07): Phase 1 ✅ 구현 완료(파서 + `contains` 엣지). Phase 2·3 예정.**

## 0. 문제

`.md`는 지금 `extractPlain`을 타고 **파일 하나 = 노드 하나**가 된다. 스팬은 파일
전체, 엣지는 0개다. `parse.go`의 주석이 그 목적을 이렇게 적어 두었다 — *"so
agents can still **discover and read** them"*. **내용 검색은 애초에 목표가
아니었고**, 그건 설계 실패가 아니라 범위 밖이다.

문제는 약속한 절반인 **read가 긴 문서에서 깨진다**는 것이다. 그리고 본문 색인
상한 때문에 **검색 효용이 문서 길이에 반비례한다** — 정작 찾고 싶은 긴 스펙이
가장 안 찾힌다.

## 1. 확정 결정

- **D1. 섹션이 원자다. 파일 노드는 유지한다.** 파일 탐색은 이미 값을 하고
  있고(파일명 `exact` 매칭), 섹션의 부모가 필요하다.
- **D2. 노드 ID = `<경로>#<슬러그>`.** GitHub 앵커와 같은 결과를 목표로 한다 —
  사람이 문서에 쓰는 링크와 기계가 쓰는 ID가 하나로 수렴한다.
- **D3. 섹션 스팬은 평면이다.** 섹션끼리 겹치지 않는다. 계층은 스팬이 아니라
  엣지로 표현한다. 부모와 자식을 함께 요청해도 내용이 중복되지 않는다.
- **D4. `contains`는 1급 엣지 타입이고 신뢰도는 1.0이다.** 구조적 사실이지
  추론이 아니다.
- **D5. 파일 노드의 `BodyTokens`는 preamble(첫 헤딩 이전)만 싣는다.** 전체를
  실으면 섹션 1과 BM25 질량이 이중으로 잡힌다.
- **D6. 요약은 두 종류이고 소비자가 다르다.** 파생 요약(헤딩 경로 + 첫 문장)은
  **벡터용**이고 graphin이 만든다. 저작 요약(1줄)은 **에이전트가 보고 판단하는
  것**이고 graphin은 만들지 않는다 — 생성 모델이 없다.
- **D7. Knowledge set은 graphin의 기능이 아니다.** 저장소의 문서 관습이고,
  저작과 소비는 `graphin-guide`의 스킬이다. graphin은 결정론적으로 쪼개고
  정확히 꺼내주는 일만 한다.

## 2. 측정 (이 저장소, 2026-08-07)

추측이 아니라 이 수치가 설계를 정했다.

| | 지금 (파일 노드) | 섹션 노드 |
|---|---|---|
| 색인되는 본문 토큰 | **23%** (7,831 / 34,088) | **93%** (31,784 / 34,088) |
| 256토큰 초과 (본문 잘림) | 파일 25/32 (78%) | 섹션 22/283 (**8%**) |
| 12KB 초과 (`read_code` 잘림) | md 8개 | 섹션 **0개** |

md 32개 → 섹션 **283개**, 토큰 중앙값 98 · 평균 120. 가장 큰 섹션이 4.9KB라
**모든 섹션이 12KB 응답 예산 안에 온전히 들어간다.**

지금 가장 나쁜 사례가 이 문서들과 같은 층에 있다:

```
 3.7%  docs/plugin-distribution.md   ← 배포·버저닝 스펙
 8.1%  internal/admin/DESIGN.md
12.4%  docs/usage-spec.md
12.6%  README.md
```

**효용이 필요도에 반비례한다.** 짧은 문서는 잘 검색되는데 짧은 문서는 애초에
검색이 덜 필요하다.

엣지 재료 (md 안의 저장소 내부 링크):

| 종류 | 개수 |
|---|---|
| md → md | 32 |
| md → 섹션 (앵커 포함) | 2 |
| md → 코드 | **0** |

**링크 그래프는 얇다.** 값을 하는 것은 `contains`이고 링크는 덤이다. 기대치를
여기에 맞춘다.

## 3. Phase 1 — 파서와 노드

### 3.1 언어 라우팅

`.md`·`.markdown`을 `parse.go`의 `plainExtensions`에서 **뺀다.** `LangMarkdown`을
신설하고 `internal/parse/markdown.go`가 `java.go`·`python.go` 옆에 선다.

다른 plain 확장자(`.yml`·`.json`·`.sql`…)는 **그대로 둔다.** 헤딩이 없어 이
개념이 성립하지 않는다.

### 3.2 헤딩 추출 — 펜스 추적은 정확성 요건이다

ATX 헤딩(`^#{1,6}\s`)만 인식한다. Setext(`===` 밑줄)는 v1에서 다루지 않는다.

**펜스(``` / ~~~) 안의 `#`는 헤딩이 아니다.** 이건 스타일 문제가 아니라 정확성
문제다 — 실측: 이 저장소에서 순진한 `^#` 분할은 **302개 중 26개(9%)가 오탐**이고,
전부 문서에 인용된 셸 스크립트의 주석이다.

tree-sitter 마크다운 문법을 새로 붙이지 않는다. 펜스 추적 + ATX 매칭은 짧고,
cgo 문법 바인딩을 하나 더 늘리는 값을 하지 못한다.

### 3.3 슬러그와 노드 ID

```
<워크스페이스 상대경로>#<슬러그>
docs/plugin-distribution.md#13-버저닝
```

슬러그 생성:

1. 소문자화
2. 문자·숫자·`_`·`-`·공백만 남기고 나머지는 **흔적 없이 지운다** (한글은 문자로
   취급되어 보존된다)
3. 남은 공백 문자 **하나가 하이픈 하나**가 된다
4. 같은 파일 안에서 충돌하면 문서 순서대로 `-1`, `-2`를 붙인다

**연속 하이픈을 축약하지 않고, 앞뒤 하이픈을 자르지도 않는다.** 이 두 가지가
틀리기 쉽고 여기서는 결정적이다 — 지워지는 문자는 아무것도 남기지 않지만
**그 문자를 감싸던 공백은 각각 하이픈이 되기 때문**이다.

규칙은 추측이 아니라 GitHub이 이 저장소를 렌더한 결과에서 읽었다
(`gh api /repos/…/contents/… -H "Accept: application/vnd.github.html"`):

```
# 플러그인 배포 스펙 — 바이너리 동봉 …  →  플러그인-배포-스펙--바이너리-동봉-…
### 3.4 부수 개선 ✅                    →  34-부수-개선-
#### 4.1 darwin/arm64 핀 (v1.1)        →  41-darwinarm64-핀-v11
### 3.1 `const` → `var`                →  31-const--var
```

**축약하는 구현이었다면 이 저장소 헤딩의 34%가 어긋났을 것이다.** 백틱·`/`·`.`·
괄호는 하이픈을 남기지 않고 사라지고, `—`·`→`·✅는 사라지되 양옆 공백이 각각
하이픈이 된다.

검증: `docs/plugin-distribution.md`의 헤딩 46개를 GitHub 실제 앵커와 대조해
**46/46 일치.**

실측: 이 저장소의 헤딩에서 **슬러그 충돌 0건.** 규칙은 있어야 하지만 아직
발화하지 않는다. 빈 슬러그(기호만 있는 헤딩)는 `section`으로 대체한다 — 여기서만
GitHub과 갈라지는데, 빈 앵커는 어차피 쓸 수 없기 때문이다.

### 3.4 노드와 스팬

| 노드 | 스팬 | Kind |
|---|---|---|
| 파일 | 파일 전체 (지금과 동일) | `file` |
| 섹션 | 헤딩 줄 시작 → **다음 헤딩(레벨 무관) 직전** | `section` |

섹션 스팬은 **평면이다**(D3). `### 13.1`은 `## 13`의 스팬에 포함되지 않는다.
`## 13`의 스팬은 자기 헤딩과 그 아래 산문까지이고, 거기서 끝난다.

이유: 배치 읽기에서 부모와 자식을 함께 요청해도 **바이트가 중복되지 않는다.**
"§13 전체"가 필요하면 세트가 자식 ID를 함께 나열한다 — 확정된 것을 정확히
가져온다는 원칙이 암묵적 확장보다 우선한다.

파일 노드의 스팬은 **파일 전체로 유지한다.** `read_code(파일)`의 기존 동작이
그대로 남는다. 섹션끼리 겹치지 않을 뿐, 부모인 파일 노드는 전체를 덮는다.

`DisplayName`·`SimpleName`은 헤딩 텍스트. `Package`는 지금처럼 디렉터리의 점
표기.

### 3.5 엣지

`schema/graph.fbs`의 `EdgeType` **끝에** `Contains`를 추가한다(끝에 붙이는 것은
FlatBuffers 하위호환이다). `make fbs`로 재생성하고 `EdgeTypeName`에 케이스를
추가한다.

| 엣지 | 방향 | 신뢰도 |
|---|---|---|
| `contains` | 부모 → 자식 (계층적, 아래 규칙) | **1.0** |
| `reference` | md → 링크 대상(저장소 내부 파일/섹션) | **1.0** |

**부모 결정 규칙**: 섹션 S의 부모는 **S보다 앞에 있으면서 레벨이 더 얕은 가장
가까운 섹션**이다. 그런 섹션이 없으면 부모는 파일 노드다.

이 한 줄이 레벨 건너뜀(h2 → h4)과 h1로 시작하지 않는 문서를 함께 처리한다.
"레벨이 정확히 1 더 깊은 것"이나 "h1이 루트"로 정의하면 둘 다 깨진다.

실측(이 저장소): **레벨 건너뜀 1건, h1로 시작하지 않는 문서 3개.** 가장자리
사례가 아니라 이미 존재하는 입력이다.

링크는 저장소 안에 존재하는 대상만 엣지가 된다. 외부 URL과 깨진 링크는 엣지를
만들지 않는다. 앵커가 붙은 링크(`x.md#섹션`)는 **섹션 노드**를 가리킨다.

### 3.6 요약 (벡터용)

`Summarize()`에 섹션 케이스를 추가한다:

```
section <헤딩 경로>: <헤딩 식별자 분해>; content <BodyTokens 앞 40개>
```

헤딩 경로는 조상 헤딩을 `›`로 이은 것(`13. 버저닝 › 13.3 0.x 규칙`). 이것이
D6의 **파생 요약**이고, 소비자는 임베딩 모델이지 에이전트가 아니다.

### 3.7 검색 결과가 바뀐다 — 의도된 변화

지금 `"플러그인 배포 스펙 바이너리 동봉"`은 **파일 노드**를 반환한다. Phase 1
이후에는 같은 질의가 **섹션 노드**를 반환한다. 더 정확하지만 **동작이 바뀌는
것이고**, 릴리스 노트에 적어야 한다.

파일은 이름·경로로 여전히 찾을 수 있다(`exact` 매칭은 베이스네임 기반).

### 3.8 한국어는 이 변경으로 고쳐지지 않는다

형태소 분석이 없어 표면형이 정확히 맞아야 BM25가 잡는다(`배선` 0건 /
`배선하지` rank 1). 섹션화는 **상한**을 고치지 토크나이저를 고치지 않는다.

다만 섹션마다 자기 임베딩이 생기고 헤딩이 이름으로 들어가므로 **한국어 내용
검색은 벡터 쪽이 짊어진다**(모델은 `multilingual_cjk`). 문서에 "BM25가 한국어
어구를 찾아준다"고 쓰지 않는다.

## 4. Phase 2 — 정확한 다중 추출

`read_code`에 **선택 파라미터 `node_ids[]`를 추가한다.** 새 툴을 만들지 않는다 —
의미가 동일하고("정확한 슬라이스를 읽는다") 기존 `node_id` 호출이 그대로
동작하므로 계약이 깨지지 않는다.

**잘림 규칙이 이 기능의 존재 이유다.**

- **섹션 중간에서 자르지 않는다.**
- 예산 안에 들어가는 노드는 **온전히** 반환한다.
- 못 넣은 것은 **ID 목록으로 명시한다.**

지금 `Truncate`는 12KB에서 내용 중간을 자른다. 단일 읽기에서는 견딜 만하지만,
"참조하기로 **결정한** 항목을 정확히 가져온다"는 요구에서는 그게 배신이다.
조용히 반쪽을 주느니 "이건 못 넣었다"고 말하는 쪽이 결정론적이다.

실측이 이걸 뒷받침한다 — 섹션 283개 중 12KB 초과 0개, 토큰 중앙값 98. 12KB
예산이면 보통 여러 섹션이 통째로 들어간다.

## 5. Phase 3 — `graphin-guide`: Knowledge set

**graphin에는 아무것도 추가하지 않는다.**

Knowledge set은 **md 문서 하나**다. 엔트리는 `노드 ID + 1줄 요약`. graphin이
특별 취급하지 않으므로 **세트 문서 자체가 섹션 노드가 된다** — 세트가 커지면
세트도 부분 로드된다.

- **저작 스킬**: 문서를 읽고 세트를 만든다. 요약을 쓰는 것은 에이전트의 일이다 —
  문서를 읽은 에이전트에게는 있고 graphin에게는 없는 능력이다.
- **소비 스킬**: 세트를 읽고 → 고르고 → `read_code(node_ids)`로 정확히 가져온다.
- **CI 가드**: 세트가 참조하는 앵커가 실제로 존재하는지. **순수 텍스트 검사라
  graphin이 필요 없다.**

에이전트 정의에는 세트 **이름 한 줄**만 둔다. 요약 목록은 필요할 때 읽으므로
**상시 컨텍스트 비용이 0**이다.

## 6. 하류 영향 ✅ 해소

`usage`의 타깃 분리는 `db.` 접두사가 아닌 것을 전부 `code`로 셌으므로, 섹션
노드가 생기는 순간 문서 조회가 **코드 질의 채택률에 섞여 들어갔다.**

**`docs` 타깃을 추가했다.** 판정은 노드 id로만 한다(이벤트에 종류가 없다):
`db.` 접두사 → db, `#` 앞의 경로가 `.md`·`.markdown`으로 끝나면 → docs, 나머지
→ code. 슬러그에는 헤딩에 쓸 수 있는 무엇이든 들어갈 수 있으므로 **`#` 앞의
경로만** 본다.

리포트와 admin `/usage`는 db 런이나 docs 런이 하나라도 있을 때만 이 절을
보여준다. code 한 줄만 나오는 표는 헤드라인 표의 반복이고, 비어 있는 db 줄이
상주하면 "db 질의가 없었다"가 "db에서 실패한다"로 읽힌다.

## 7. 검증

```sh
go test ./internal/parse/     # 펜스 안 #, 슬러그 충돌, 스팬 경계
go test ./internal/graph/     # contains 엣지 방향과 신뢰도
make fbs && git diff --exit-code internal/graph/fbsgen/   # 재생성이 결정론적인지

# 이 저장소 자신이 픽스처다: 헤딩 276개, 펜스 오탐 26개, 슬러그 충돌 0건
```

### 7.1 Phase 1 실측 (2026-08-07)

새 바이너리로 저장소 사본을 인덱싱해 스펙의 예측을 그대로 확인했다.

| 확인 | 결과 |
|---|---|
| `search_hybrid "프렐류드"` | `docs/markdown-spec.md#7-검증` **`match_type="lexical"`** — 이 질의는 지금까지 렉시컬 0건이었다 |
| `explore_graph …plugin-distribution.md` | `contains` **1개**. h1이 하나뿐이고 계층적이므로 파일의 직계 자식은 그 h1이다 (레벨 분포: h1 1 · h2 14 · h3 28 · h4 3) |
| `explore_graph …#13-버저닝` | `contains` **6개** (13.1 ~ 13.6), 전부 `confidence="1.00"` |
| `read_code …#133-0x-규칙` | **653바이트, `lines="906-924"`, 절단 없음.** 같은 문서를 파일 노드로 읽으면 57KB 중 12KB에서 잘린다 |

슬러그는 `docs/plugin-distribution.md`의 헤딩 46개를 GitHub 실제 앵커와 대조해
**46/46 일치**를 확인했다.

## 8. 하지 말 것

- **펜스 추적 없이 `^#`로 자르기** — 이 저장소에서만 9%가 오탐이다.
- **섹션 스팬을 계층적으로(자식 포함) 잡기** — 부모와 자식을 함께 읽으면 내용이
  중복된다. 계층은 엣지의 일이다.
- **파일 노드 제거** — 파일 탐색이 지금 값을 하고 있고, 섹션의 부모가 필요하다.
- **`.yml`·`.json` 등을 같이 쪼개기** — 헤딩이 없다.
- **graphin에 요약 생성 붙이기** — 로컬·무네트워크·API 키 없음이 제품의
  전제다. 생성은 에이전트의 일이다.
- **배치 읽기에서 섹션 중간을 자르기** — 확정된 참조를 반쪽으로 주는 것은
  결정론이 아니다.

## 9. 열린 질문

- **서브트리 읽기.** D3(평면 스팬)의 결과로 "§13 전체"는 자식 ID를 나열해야
  한다. `read_code`에 `subtree: true`를 둘지, 세트 저작 시점에 펼칠지.
- **요약 rot.** 텍스트 가드는 앵커 존재만 잡고 "내용이 바뀌었는데 요약이 그대로"는
  못 잡는다. graphin은 이미 노드별 해시를 갖고 있으므로(`merkle.json`,
  `NodeMeta.FileHash`) 세트에 저작 시점 해시를 적어 두면 결정론적 stale 탐지가
  된다 — **graphin이 낡았다고 말하고 guide가 다시 쓴다.** Phase 4 후보.
- **Setext 헤딩**(`===` 밑줄). 이 저장소에 0건이라 v1에서 뺐다.
- **`docs` 타깃** (§6).
