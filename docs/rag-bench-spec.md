# rag 벤치 — graphin-rag 행동 골든셋

`eval/rag/{tasks,expected}.jsonl`과 `scripts/eval-rag.py`가 이루는 벤치마크의
표준. 수치·가중치·판정 규칙의 **정본은 문서가 아니라 채점기 코드**이고
(`scripts/eval-rag.py`의 `RUBRIC_VERSION`), 이 문서는 각 축이 왜 있는지와
결과를 어떻게 읽어야 하는지를 적는다.

## 0. 무엇을 재나

`eval/golden` + `scripts/eval-recall.py`는 검색 호출 한 번의 recall을 재는
결정론 측정이다. 이 벤치는 그 위층 — **graphin-rag 서브에이전트 루프 전체의
행동**을 잰다: 답이 맞았는가만이 아니라, 예산을 지켰는가, 자기 지출을 정직하게
보고했는가, 힌트를 따랐는가, 없는 것을 없다고 말했는가.

실행 단위는 SWE-bench의 인스턴스에 해당하는 태스크다. 러너가 저장소 스냅샷을
떠서 인덱스하고, 실제 에이전트 정의(`plugin/graphin-guide/agents/graphin-rag.md`
+ graphin 스킬, 플러그인이 주입하는 그대로)를 헤드리스로 태워 트랜스크립트
전체를 캡처하고, 결정론 채점기가 등급을 낸다. LLM 저지는 없다.

## 1. 층은 에이전트의 종료 상태다

층 구성이 에이전트 계약(graphin-rag.md의 세 종료 상태)을 그대로 따른다.
프롬프트의 계약이 바뀌면 골든셋이 따라 움직여야 한다는 사실이 이 구조로
명시된다.

| 층 | 재는 것 |
|---|---|
| `answered` | 내용 질문 — 근거가 최종 보고서까지 도달했는가 |
| `multi-hop` | 정의만 읽어서는 안 되고 엣지 건너편이 필요한 질문 |
| `not-here` | 존재하지 않는 것 — 없다고 말하는가, 그럴듯한 쓰레기를 인용하는가 |
| `out-of-reach` | graphin이 답할 수 없는 것(런타임 값·로그) — 한계를 말하는가 |
| `budget-pressure` | 좁힌 예산(20KB) 아래서 압축하거나, 절단을 **말하고** 멈추는가 |
| `db-nav` | 스키마 내비게이션과 그 엣지케이스 — 스냅샷 밖 FK 타깃, enforced=false, 크로스 datasource/엔진, enabled=false RLS, 트리거→함수 링크, 텍스트로만 있는 테이블명 |

층을 섞은 단일 평균은 내지 않는다 — 서로 다른 질문들의 가중 평균은 아무
뜻도 없다는 원칙은 eval-recall과 같다. `db-nav`만 예외적으로 **층 안에서
종료 상태를 섞는다**(answered·not-here·out-of-reach): 이 층의 축은 판정
모양이 아니라 코퍼스(DB 스키마)다. 스모크 서브셋에는 넣지 않았다 — patch
게이트의 속도 목표가 우선이고, minor의 풀셋이 이 층을 덮는다. 코퍼스에
같은 사실의 표현이 여럿일 수 있음(rls 사이드카 JSON과 dbssot schema.sql)이
이 층에서 드러났고, 그래서 must_cite도 `|` 대안을 갖는다.

## 2. 파일 형식

`eval/rag/tasks.jsonl`(질문)과 `eval/rag/expected.jsonl`(정답)은 **일부러
분리**되어 있고 id가 같은 순서로 1:1 대응해야 한다. `.jsonl`인 이유도
`eval/golden`과 같다: 색인되지 않는 확장자라 질의문이 자기 답으로 검색되는
오염이 없다. 이 문서에 질문 본문을 적지 않는 이유도 같다 — 이 파일은 색인된다.

`expected` 한 줄의 필드:

- `end_state` — `answered` | `not-here` | `out-of-reach`.
- `must_cite` — 최종 보고서가 인용해야 하는 저장소 상대 경로들. 답이 여러
  파일에 걸치면 다 적는다.
- `evidence` — 보고서 본문에 **반드시 들어 있어야 할** 리터럴들(AND). 한
  항목 안에서 `a|b|c`는 대안이다: 사실이 전달되면 되지, 한 철자를 강요하지
  않는다. 검증기는 각 항목이 must_cite 파일 어딘가에 실재하는지 확인한다.
- `evidence_any` — 하나만 있으면 되는 리터럴들(OR, 대소문자 무시).
- `forbidden` — 날조된 답에만 나올 문자열. not-here 층의 환각 검출용.
  **부정 문맥 안의 등장은 세지 않는다** — "찾아봤지만 `func X`는 0건"은 금지
  리터럴을 인용한 모범 답안이고, 1.0.0이 이걸 실격시켰다가 1.0.1에서 고쳤다.
- `subject` — not-here 층 전용. "부재를 말했다" 판정은 이 토큰과 부정어가
  같은 문장에 있는가로 낸다.
- `why` — 사람을 위한 근거 메모.

## 3. 루브릭 — 세 축과 판정

**정답 축**: must_cite 전부 인용 + evidence 전부 전달 + evidence_any 하나
이상. 인용된 경로가 스냅샷에 실재하지 않으면 fake citation으로 실격급이다.

**비용 축**: 툴 결과 바이트 합(트랜스크립트에서 직접 합산 — 서버의 자기
보고를 믿지 않는다), 예산 준수, 그리고 **자기 보고 정확도** — 보고서의 Cost
절이 말한 숫자를 실측과 비교한 비율. 예산 초과 자체는 실격이 아니고, **말없는
초과**(`over_silent`)만 실격이다 — 계약이 금지하는 것은 지출이 아니라 침묵이다.

**행동 축**(관찰 지표, v1에서는 게이트 아님): 지어낸 node id(이전 응답에 없던
id를 넘김 — 트랜스크립트로 완전 검증 가능), 힌트 순응, 연속 재검색 길이,
read_code 배칭. 계약의 금지 조항을 그대로 검출기로 옮긴 것들이다.

not-here는 forbidden·fake 없이 부재 문장이 있으면 pass, 부재 문장이 없는데
날조도 없으면 **inconclusive**로 따로 센다 — 이 지표의 고장 방향은 실패의
과대보고이므로 애매함을 실패로 세지 않는다. out-of-reach는 무엇이 부족한지
말하면(evidence_any) pass다.

**루브릭 버전 규칙.** 판정 규칙·축을 바꾸면 `RUBRIC_VERSION`을 올리고,
`docs/eval/`에 날짜 디렉터리로 재베이스라인을 남긴다. 러너 거동(프롬프트·
스냅샷 코퍼스·도구 로스터)을 바꾼 버전과 채점 규칙만 바꾼 버전은 다르다:
전자는 호환 목록(`RUN_COMPAT`)을 새 버전 하나로 리셋해 옛 런의 재채점을
거부하고, 후자는 목록에 붙어 기존 트랜스크립트를 재채점할 수 있다. 리포트에는
채점기 자신의 버전이 찍히고, 비교는 같은 (러너 시대, 루브릭) 안에서만 한다.

## 4. 러너가 격리하는 것, 못 하는 것

- `--bare`를 쓰지 않는다. bare는 OAuth를 절대 읽지 않아 이 계정 인증이
  불가능하다. 대신 `--settings`로 훅 전부(위키 게이트가 측정 대상 도구를
  막는다)와 플러그인을 끄고, `--strict-mcp-config`로 MCP는 러너가 띄운 서버
  하나만 쓰고, cwd를 스냅샷에 둬 CLAUDE.md·자동 메모리가 해석되지 않게 한다.
- 스냅샷은 `git ls-files` 기준 사본이고 러너가 미리 인덱스한다(런마다
  재인덱스하는 27배 증폭을 피한다). `.graphin/*`은 git-ignore라 usage 로그
  같은 런타임 데이터는 스냅샷에 없다.
- **측정 장치는 스냅샷에서 잘라낸다**(`eval/rag`·`eval/golden`·골든셋 스킬·
  `scripts/eval-*`). `.jsonl`은 색인만 막을 뿐인데 `search_keyword`는 파일을
  읽는다 — not-here의 금지 리터럴이 expected.jsonl에, 한 번은 채점기 주석에
  실재해서 "없다"가 거짓이 됐다. eval-recall은 자기 파일을 남기고 보고만
  하지만, 여기서는 그 파일들이 답 자체를 바꾸므로 배제가 맞다.
- 기본은 lexical-only다(`--ort-lib /nonexistent-ort`) — 게이트가 머신의
  캐시 사정에 좌우되면 안 된다는 eval-recall의 규칙. `--semantic`은 별도
  축으로 돌린다.
- **못 격리하는 것: 스킬 텍스트가 시스템 프롬프트에 있다.** 도구 응답 계약을
  묻는 태스크는 에이전트가 검색 없이 프롬프트에서 답할 수 있다. 그래서 정답
  축이 **인용을 요구한다** — 프롬프트에서 답을 알아도 코드로 뒷받침하지
  않으면 fail이고, 그것이 계약("인용 없는 요약은 답이 아니다") 그대로다.
- **도구 로스터는 `--allowedTools`가 아니라 `--disallowedTools`로 자른다.**
  전자는 print 모드에서 권한 허용목록일 뿐이라 나머지 도구가 전부 살아 있고,
  1.2.x 베이스라인에서 65런 중 21런이 그 밖으로 나갔다 — 여덟은 **다른
  서브에이전트에게 위임**(그 검색은 원장에 안 잡혀 예산 축이 과소 계상),
  셋은 **설치된 graphin 바이너리로 실제 저장소**를 조회(스냅샷이 일부러 도려낸
  코퍼스). 1.3.0부터 Agent·Task·Skill·ScheduleWakeup·WebFetch·WebSearch를
  로스터에서 제거한다(플래그가 실제로 제거함을 확인).
- **Bash·Read·Grep·Glob은 남긴다.** 프로덕션 graphin-rag는 쓰기 도구만
  금지하므로, grep 폴백을 뺏으면 출하되는 것과 다른 에이전트를 재게 된다
  (1.2.x까지 스펙이 "Bash를 안 준다"고 적었으나 사실이 아니었다 — 러너가
  아니라 문서가 틀렸다). Bash가 남긴 유일한 우회로는 채점이 잡는다:
  스냅샷 밖 절대 경로를 부른 런은 `escaped`로, 무엇을 답했든 pass가 아니다.

## 5. 판정 절차

- 기본 `--runs 3`. 결론은 태스크(인스턴스) 단위 pass율과 짝 비교로 내린다.
  집계 평균 하나로 결론 내지 않는다 — 이 저장소는 그 모양으로 결론이 뒤집힌
  적이 있다(2026-07-25 H1 재검증).
- 긴 런은 `--detach`로 자기 분리한다(setsid nohup). 러너는 완주 때만
  `summary.json`을 남기고, **채점기는 그 표식 없는 디렉터리를 거부한다** —
  부분 산출물이 N을 속이는 사고를 채점기 쪽에서 막는다. 죽은 런의 디렉터리는
  즉시 지운다.
- 리포트는 `report.md`(사람)과 `report.json`(기계)으로 나온다. 본 런의
  결론은 `docs/eval/YYYY-MM-DD-*/findings.md` 관례로 남긴다.

## 7. 모니터링 중 — 지어낸 노드 id

**무엇을 세나.** 리포트의 `invented node ids` — `read_code`나 `explore_graph`에
넘긴 id가 그 시점까지의 어떤 툴 응답에도 없었던 런의 수. 트랜스크립트로
완전히 검증되는 지표라 판정에 재량이 없다.

**실측 추이.** 0/57 (1.0.3, 통합 전) → **6/81 (1.3.0, 통합 후)**.

**왜 게이트가 아니라 모니터링인가.** 여섯 런 모두 **추측이 맞아서 통과**했다.
예: `rag-lock-steal` r2가 `internal.lock.Acquire` 하나를 본 뒤
`internal.lock.isLive`·`internal.lock.start`·`internal.lock.pidAlive`를
작명 규칙에서 추론해 넘겼고, 셋 다 실존했다. 정답 축이 잡지 못하는 종류의
결함이라 **별도로 센다** — 맞은 추측은 아무것도 가르치지 않고, 빗나간 추측은
**부재처럼 보인다**(계약이 "이전 호출이 돌려준 id만"이라고 못박은 이유가
그것이다).

**무엇을 보고 판단하나.** 원인 후보 둘이 이 런으로는 갈리지 않는다 —
통합으로 길어진 프롬프트에서 규율 하나가 밀린 것인지, 신설한 "값싼 경로로
빨리 멈춰라"가 추측을 부추긴 것인지. 다음 재베이스라인에서 ⓐ 비율이 더
오르면 프롬프트 조항의 위치를 손보고, ⓑ 0 근처로 돌아오면 변동으로 기록하고
닫는다. 어느 쪽이든 **결론은 인스턴스 단위로 낸다**.

**게이트 승격 조건.** 지어낸 id가 실제로 **빗나간** 런이 한 건이라도 나오면
그때는 관찰이 아니다 — 부재 오보는 이 도구가 팔 수 없는 실패다. 그 시점에
`escaped`처럼 판정 자체를 비-pass로 바꾼다.

**어디에 쌓이나.** 릴리스 게이트의 수치는 [`docs/eval/gate-log.md`](eval/gate-log.md)에
한 줄씩 남는다 — 게이트 산출물은 스크래치에 나오고 마커는 git-ignore라, 적지
않으면 통과한 순간 사라진다. 그 대장이 지켜보는 두 번째 항목이 **게이트가
5분을 넘기는 이유**(out-of-reach 태스크의 스냅샷 밖 탐색이 벽시계를 태운다)이고,
예방책(자식 세션의 경로 훅)은 범위가 과해 보류된 상태다.

## 8. 유지 결정 — 스킬이 답을 서술하는 태스크 (2026-09-01 소유자 결정)

`rag-read-omission`은 1.3.0 재베이스라인에서 0/3이었고, 세 런 모두 리트리벌
0바이트였다. `read_code`의 예산 생략 계약을 **graphin 스킬 본문이 거의 그대로
서술**하기 때문이다. 교체 후보로 올렸으나 **유지하기로 했다.**

이유는 이 태스크가 재는 것이 검색 품질이 아니라 **인용 규율**이기 때문이고,
그 규율이 지켜지는 한 **스킬 본문 자체가 색인 대상이 될 필요가 없다**는 이점이
따라오기 때문이다 — 에이전트가 아는 것을 인용 없이 말하지 않는다면, 스킬이
서술하는 사실도 결국 코드에서 확인되어 나온다. 이 태스크의 실패는 그 규율이
깨진 순간을 가리키는 유일한 신호다.

따라서 이 태스크의 0/3은 **세트의 결함이 아니라 열린 관찰 항목**이다. 통과로
바꾸려면 태스크가 아니라 에이전트 프롬프트가 움직여야 한다.

  기존 보류와 정합하게, v1 세트에는 없다.
- **grep-only 대조군은 v2** — 같은 질문을 grep 루프 프롬프트로 돌린 짝 비교.
  판단 기준이 토큰 이코노미인 이상 결국 필요하다.
- 행동 축을 게이트로 승격할지는 베이스라인 데이터가 쌓인 뒤 정한다 — 지표를
  먼저 게이트로 만들면 측정이 목표가 된다.
- 세트 재구성 절차와 오염 방지 규칙은 `.claude/skills/rag-golden-set`의
  것이다. 골든셋 작성에 graphin을 쓰지 않는다는 절대 규칙도 거기 있다.

## 8. 변경 통제와 릴리스 게이트 (2026-09-01, 소유자 결정)

**릴리스 게이트 — Claude Code 단에서, 릴리스 자리에 따라 계층으로 잠근다.**
API 과금 CI 벤치가 아니라(소유자 결정: 그 방식은 기각), 릴리스를
**디스패치하는 쪽**이 잠긴다. 무엇으로 열리는지는 버전의 어느 자리가
움직이는가가 정한다(2026-09-01 소유자 결정):

| 릴리스 | 요구 | 실행 | 시간 |
|---|---|---|---|
| minor 이상 (0.X / X.0) | **풀셋** 19태스크 × 3런 | `run --out <새 디렉터리> --runs 3 --detach` | ~1시간 |
| patch (0.x.Y) | **스모크** `SMOKE_TASKS` 6태스크 × 1런 | `run --out <새 디렉터리> --subset smoke --jobs 3` | 수 분 — **요청 후 5분 내 디스패치가 목표** |
| 성능 무관 변경 | **waive** — 메인 에이전트의 판단 | `waive --reason "…"` | 즉시 |

공통 규칙: 측정은 릴리스할 커밋(푸시된 HEAD)에서, `--worktree` 금지.
`score --out <디렉터리> --gate 0.80` 통과가 커밋-바인딩 마커
`.graphin/rag-gate-pass.json`을 발행하고(mode: full/smoke — 스모크 마커는
patch만 연다, 임의 서브셋은 `partial`로 아무것도 열지 않는다), 새 커밋이
얹히면 만료다. error·inconclusive는 비-pass. 근소 미달은 게이트 재실행이
곧 재측정이고 숫자를 내리는 것은 재측정이 아니다.

**스모크 구성 원칙.** 2026-09-01 베이스라인에서 3/3이던 태스크만으로 4개
층을 하나씩 이상 덮는다 — 스모크의 실패는 주사위가 아니라 변경을 뜻해야
한다. budget-pressure는 변동성이 커서 일부러 뺐고, 그 층은 minor 릴리스의
풀셋이 덮는다. 표본 6에서 플로어 0.80은 5/6이다.

**waive — 위임된 판단과 그 레일.** 소유자는 "성능에 영향을 주지 않는
변경이면 rag 테스트를 생략한다"는 판단을 메인 에이전트에게 위임했다.
판단은 기록되고(`rag-gate-waiver.json`: 커밋·사유·근거 diff), 레일이 있다:
직전 태그 이후 diff가 측정 관련 경로(`SENSITIVE_PREFIXES` — internal/*,
guide 플러그인, 벤치 자신; `internal/console`·`usage`·`wiki`는 예외)를
하나라도 건드리면 `waive`가 거부하며, 이 레일은 여기서 넘을 수 없다 —
넘으려면 보호 파일을 고치는 일이 되어 변경 통제에 걸린다. release
에이전트는 waiver를 받아들이되 **사유를 릴리스 보고서에 인용**한다.

집행은 두 겹이다: `.claude/hooks/release-gate.sh`(PreToolUse Bash 훅)가
디스패치 명령(`gh workflow run …release…`, `gh release create`, dispatch
API)을 가로채 버전 자리를 파싱해 위 표를 강제하고 — 메인 세션이든 release
서브에이전트든, 버전을 파싱할 수 없으면 엄격한 쪽(풀셋)으로 — `release`
서브에이전트 §1이 같은 검증을 먼저 한다. 측정은 호출자의 단계, 검증은
에이전트의 단계다.

"5분"의 정직한 범위: 게이트(스모크 ~2–4분) + 디스패치까지다. 디스패치 뒤
워크플로의 빌드·퍼블리시·verify(~15–20분)는 이 손잡이 밖이다. 풀셋은 세션
사용량 한도를 상당히 쓴다 — 하루 여러 번이면 429.

**변경 통제.** 루브릭(`scripts/eval-rag.py`)과 테스트 케이스(`eval/rag/*`)의
추가·수정·삭제는 **저장소 소유자의 명시적 허가가 있을 때만** 한다. 이 규칙은
세 겹으로 박혀 있다:

1. **해시 락** — `eval/rag/rubric.lock`이 보호 파일들의 sha256을 기록하고,
   CI와 릴리스 게이트의 `verify-lock`이 드리프트를 실패로 만든다. 갱신은
   허가를 받은 뒤 `scripts/eval-rag.py lock --approved-by <소유자>`로만.
2. **커밋 트레일러** — 보호 파일을 건드린 커밋은
   `Rag-Bench-Approved-By:` 트레일러를 달아야 CI를 통과한다. 허가의 기록이
   히스토리에 남는다.
3. **세션 훅** — Claude Code 세션에서 보호 파일에 대한 Edit/Write가
   거부된다. 저장소 루트의 `.rag-bench-unlock` 파일이 있을 때만 열리고,
   작업이 끝나면 지운다. **누가 여는가**: 소유자가 직접 만들거나, 소유자가
   해당 변경을 **이 세션 대화에서 명시적으로 지시했을 때에 한해** Claude가
   만들고 작업 직후 삭제한다(2026-09-01 소유자 운용 방식에 맞춰 명문화).
   지시 없는 자체 판단으로 Claude가 이 파일을 만드는 것은 위반이다.

한계를 적어 둔다: 훅은 Bash 경유 수정을 막지 못하고(그건 락과 트레일러가
CI에서 잡는다), 단독 소유자 저장소에서 이 통제는 암호학적 강제가 아니라
**모든 변경을 시끄럽고 명시적으로 만드는 장치**다. 더 굳히려면 GitHub 쪽
branch protection이 소유자의 몫이다. 플로어 0.80 자체, 그리고 이 절의 규칙
변경도 같은 통제를 받는다.
