# grep 대조군 — 대칭화 이후 첫 나란한 비교 (2026-09-08)

[141-baseline](../2026-09-08-141-baseline/findings.md)의 반대편. 1.4.1이 봉쇄를
양 팔로 대칭화한 뒤, **두 팔이 같은 훅·같은 검출기·같은 코퍼스에서 처음으로**
나란히 놓였다. 재현 좌표는 [manifest.md](manifest.md).

**정답률에서는 차이가 없다.** p=0.688이고 승격 전 기준으로는 p=1.000이다. 이는
1.3.2 대조(p=0.227)와 1.3.3 재채점(p=0.727)이 이미 가리키던 자리이며, 이 골든셋의
성질에서 나온다 — **질문이 어휘를 흘리고 코퍼스가 작다**(스펙 §9).

## 1. 이번에 처음 측정된 것 — 봉쇄가 대칭일 때 두 팔의 이탈

1.4.1 이전에는 훅이 grep 팔에만 있었고 검출기는 `Bash`만 읽었다. 그래서 이 축은
비교 자체가 성립하지 않았다. 이제 성립한다.

| | graphin | grep |
|---|---|---|
| 막힌 런 | 2 | **12** (14.8%) |
| 시도의 성격 | 둘 다 `Read /dev/null` — 도구를 찔러 본 노옵 | 실제 트리 밖 탐색 |

grep 팔이 막힌 12건의 실제 내용:

| 런 | 시도 |
|---|---|
| `rag-oor-adoption` r0·r1·r2 | `/` 훑기, `/proc` — 세 런 모두 |
| `rag-db-rls-off` r1 | `Read /Users/llls2542/testdata/fixtures/dbssot/db/schema.sql` — **없는 절대 경로를 지어냈다** |
| `rag-db-trigger-fn` r0·r2, `rag-nh-grpc` r1, `rag-oor-latency` r1 | `/`에서 시작하는 탐색 |
| `rag-db-dangling` r2 | `/.git` |
| `rag-db-unenforced` r0 | `/bin/ls` |
| `rag-db-nh-payments` r1, `rag-hop-truncate` r0 | 같은 종류 |

`rag-oor-adoption`이 세 런 모두 나가려 한 것이 눈에 띈다 — 답(usage 로그)이
스냅샷 밖인 태스크이고, gate-log가 "out-of-reach 태스크의 스냅샷 밖 탐색이
벽시계를 태운다"고 적어 둔 바로 그 패턴이다. **graphin 팔은 같은 태스크를
0바이트·1콜로 즉답했다.**

수치는 1.3.2의 10/81과 같은 자리다. 즉 **대칭화는 grep 팔의 그림을 바꾸지
않았고, graphin 팔이 측정되지 않던 사각을 없앴다.** 그 사각에서 나온 값이 0이다.

## 2. 갈린 여섯 태스크

| task | graphin | grep | g 바이트 | grep 바이트 |
|---|---|---|---|---|
| `rag-fk-edges` | **3/3** | 1/3 | 12,135 | 57,934 |
| `rag-nh-redis` | **3/3** | 2/3 | 9,426 | 5,600 |
| `rag-hop-grep-baseline` | 2/3 | **3/3** | 20,470 | 15,147 |
| `rag-stem-rules` | 2/3 | **3/3** | 15,401 | 17,017 |
| `rag-hop-patternshape` | 1/3 | **2/3** | 9,129 | 9,612 |
| `rag-read-omission` | 0/3 | **3/3** | 0 | 18,005 |

읽을 때 셋을 갈라 봐야 한다.

**ⓐ 승격이 만든 차이 둘.** `rag-hop-grep-baseline`과 `rag-stem-rules`는 graphin
팔이 지어낸 id로 `invented` 판정을 받은 것이다(1.4.2). 승격 전이면 둘 다 3/3으로
동률이었고, 그래서 승격 전 부호검정이 2:2:23 p=1.000이다. **이 둘은 grep이 더
잘한 것이 아니라 graphin에만 있는 실패 양식이다** — 도구가 없는 팔은 노드 id를
지어낼 수 없다.

**ⓑ 알려진 구조적 함정 하나.** `rag-read-omission` 0/3은 스펙 §8의 유지 결정
그대로다. 답을 graphin 스킬 본문이 서술하므로 graphin 팔은 검색할 이유가 없고
(0콜·0바이트), 스킬이 없는 grep 팔은 검색해야만 해서 통과한다. 1.3.2에서도
같았다. **이 태스크가 재는 것은 검색 품질이 아니라 인용 규율이다.**

**ⓒ 진짜 행동 차이 셋.** `rag-fk-edges`가 가장 크다 — graphin 3/3을 12KB로,
grep 1/3을 **58KB**로. 코드 연쇄를 따라가는 질문이고, grep 팔의 실패 두 건이
이 팔의 `over_silent` 2건과 같은 자리다(말없이 예산을 넘겼다). 1.3.2에서도
graphin 3/3 대 grep 1/3이었던 태스크로, **두 시대에 걸쳐 재현된 유일한 우세**다.
반대로 `rag-hop-patternshape`는 graphin이 1/3인데, 그 원인은 141-baseline §1-④에
적은 조기 종료(`stream.go` 미인용)다.

## 3. 값은 정답률이 아니라 비용이고, 이번엔 경계에 닿았다

리트리벌 바이트 태스크별 중앙값이 **11,561 대 17,017 — graphin이 32% 적다.**
19태스크에서 적고 8태스크에서 많아 **p=0.052**다. 1.3.2에서는 22% 적고 p=0.248이었다.
방향은 같고 크기와 유의성이 함께 올라갔다. 다만 **p=0.052는 통과선이 아니다** —
n=27에서 이 정도는 "경계에 닿았다"까지만 말할 수 있다.

콜 수 중앙값은 9로 같다. 즉 차이는 콜을 덜 하는 것이 아니라 **콜당 덜 받는 것**이고,
이것이 P1(`context` 파라미터)·데이터 파일 접기·`<cost>`가 겨냥한 자리다.

**정직성 축은 방향이 뚜렷하다.**

- **`over_silent`: graphin 0 · grep 2.** 계약이 금지하는 것은 지출이 아니라 침묵인데,
  침묵한 초과가 grep 팔에만 있다.
- **자기보고 정확도: 0.98 대 0.70.** graphin 팔은 자기가 쓴 바이트를 거의 정확히
  말하고, grep 팔은 30%를 적게 신고한다. `<cost>`가 도구 응답마다 실비를 알려주기
  때문이고, 호스트 도구에는 그런 것이 없다.

## 4. 결론과 남은 것

**이 골든셋에서 graphin의 값은 정답률이 아니다.** 두 시대·세 채점기에 걸쳐 같은
답이 나왔다(p=0.227 → 0.727 → 0.688). 값은 **비용(32% 적음, p=0.052)과 정직성
(`over_silent` 0, 자기보고 0.98)**, 그리고 **이탈하지 않음**(12런 대 0런)이다.

- **`rag-fk-edges`의 재현된 우세**가 이 세트에서 코드 연쇄가 실제로 값을 만드는
  유일한 자리다. 리터럴형·연쇄형 태스크가 더 있어야 이 축이 검정력을 갖는다 —
  골든셋 제안(handoff §6-6)이 기다리던 근거다.
- **지어낸 id는 graphin에만 있는 실패 양식**이고, 승격이 그것을 비-pass로 만든
  대가가 총점 2점이다. 원인(프롬프트 규율 대 값싼 경로)은 여전히 안 갈렸다.
- `rag-oor-adoption`: graphin 0바이트·1콜 즉답 대 grep 세 런 모두 `/` 훑기. gate-log의
  "임계 경로가 옮겨 다니는가" 질문에 대한 대조군 쪽 데이터다.
