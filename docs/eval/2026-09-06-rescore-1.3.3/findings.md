# 표기를 고치면 6점 차가 3점이 되고, 그 3점은 소유자가 유지한 태스크 하나다 (2026-09-06)

인수인계 §0의 비판 둘 중 첫째 — "채점 표기 문제를 매 런 세기만 하고 고치지 않았다" —
를 닫는 재채점이다. 루브릭 1.3.3(규칙은 [manifest](manifest.md)), 새 런 없음, 같은
트랜스크립트. 비교의 정본은 여전히 태스크 단위 부호검정이다(스펙 §5).

**결과: grep 에이전트 76/81, graphin 에이전트(변경 전 바이너리·프롬프트만 변경·
lexical-only) 73/81.** 태스크 짝 비교에서 grep 우세 5, graphin 우세 3, 동점 19 —
부호검정 p=0.727. 1.3.2에서는 75 대 69, 8·3·16, p=0.227이었다. 표기 보정이 6점 차의
절반을 지웠고, 남은 3점은 전부 `rag-read-omission`(grep 3/3 · graphin 0/3, 소유자가
"유지"로 결정한 태스크, [스펙 §8](../../rag-bench-spec.md#8-유지-결정--스킬이-답을-서술하는-태스크-2026-09-01-소유자-결정))이다.
그 태스크를 빼면 **양 팔 73/78로 같다.** 바이트는 채점과 무관하니 그대로다 — graphin이
태스크 중앙값 13.7K 대 16.8K로 적고 27태스크 중 17에서 더 싸다.

## 3. 무엇이 확립됐나

- **grep 대조군 결과의 절반은 채점기 표기였다.** 09-06 findings가 "6점 차의 5점은
  표기와 프롬프트-에코"라 추정한 것이 실측으로는 3점(표기) + 3점(read-omission)이다.
  표기가 만든 차이는 이제 0이다.
- **이 골든셋에서 grep 에이전트와 변경 전 graphin 에이전트는 정답률로 갈리지 않는다**
  (p=0.727, 소유자 유지 태스크 밖에서 73 대 73). 09-06의 결론("graphin의 값은 정답률이
  아니다")이 더 강해졌다. 값이 있다면 바이트(−19%)와 코드 연쇄 질문(fk-edges)이다.
- **D 팔(P1 바이너리 + 하이브리드)의 비교 상대가 이제 정직하다.** D−B가 도구 효과,
  D−C가 graphin 대 grep — 둘 다 1.3.3으로 채점한다.

## 4. 열린 것 (소유자 결정)

1. **검색 로그 안의 금지 리터럴.** "무엇을 검색했나" 목록에 리터럴을 적는 것은 날조인가?
   1.3.3의 승인 범위(앞 60자 창)에 없어 그대로 fail로 두었다. 규칙을 넓히면(예: 문장
   안에 `search`·`checked`·`grep` 같은 검색 동사가 있으면 부정 문맥으로) B r2 하나가
   구제되지만, 그 어휘는 날조 문장에도 흔하다. 세기만 한다.
2. **점을 포함한 금지 리터럴은 원래부터 죽어 있다.** 문장 규칙이 `.`에서 자르므로
   `redis.Client`·`graphin.proto`·`grpc.NewServer`는 어느 조각에도 통째로 들어가지 않아
   절대 발화하지 않는다 — not-here 세 태스크의 금지어 7개 중 3개. 1.3.3은 이 동작을
   **그대로 두었다**(승인 범위 밖이고, 고치면 판정이 엄격해지는 방향이라 재베이스라인
   비교가 깨진다). 고치려면 루브릭 1.3.4+, 소유자 허가.
3. **창을 줄바꿈에서 끊은 것**은 인수인계 §7-1보다 보수적인 구현이다. 세 팔 어디서도
   결과가 갈리지 않았지만, 규칙의 문면은 이 기록이 정본이다.
