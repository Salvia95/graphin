# 2026-11-24 — 도구 계약 재설계: skill 없는 서브에이전트 측정

[도구 계약 스펙](../../tool-contract-spec.md) §5의 측정. 질문은 하나다 — **graphin MCP 도구만 주입되고
skill도 graphin-rag 프롬프트도 없는 서브에이전트**(플러그인으로 들어간 다른 프로젝트의 모양)에게, 도구 설명
교체·이름 입력·연쇄 응답이 도움이 되는가, 그리고 연쇄 응답을 **기본값**으로 바꿔야 하는가.

## 정정 — 바이트는 비용이 아니다 (같은 날, 토큰 재분석)

이 문서의 "바이트"는 채점기의 `bytes_total` — 에이전트가 받은 **도구 결과의 크기**다. 채점기가 그것을 쓰는 것은
에이전트 계약의 예산 축(40KB를 지켰나, 넘겼으면 말했나)을 판정하기 위해서이고, 비용 지표가 아니다. 실제 비용은
모델이 처리한 토큰이며, 매 턴 시스템 프롬프트·도구 정의·이전 결과 전부를 다시 읽는다. 게이트 세트 런 중앙값으로
도구 결과는 13KB(≈3K 토큰)인데 처리한 입력은 ≈10만 토큰이다. 같은 트랜스크립트를 토큰으로 다시 셌다
(`scripts/eval-rag-tokens.py`, [tokens.txt](tokens.txt) · [r3-tokens.txt](r3-tokens.txt)).

- 그래서 아래 판정 2·3의 **"바이트 동일·+12%(유의하지 않음)"는 비용으로는 틀린 진술이다** — B는 정답률이 같은
  채로 입력 토큰을 유의하게 더 쓴다. 남는 개선은 도구 선택(graphin 안 쓴 런 32 → 9)과 입력 모양뿐이다.
- 판정 1(연쇄 기본값 C를 두지 않는다)은 토큰으로도 같은 방향이다(비용 ×1.14).
- 후속: 설명을 비용에 맞게 줄였다(`342d29c`, 네 도구 스키마가 작업 전 대비 +515자). 재측정은 별도 문서에 둔다.

## 판정

**1. 연쇄 응답을 기본값으로 바꾸지 않는다.** C는 B보다 정답이 유의하게 낮고(1:8, p=0.039) 바이트가 유의하게
많다(+40%). 스펙 §5 기준 셋(정답 +10%p, 바이트 +30% 이내, 호출 수 이하) 중 호출 수만 충족한다. 잃은 자리는
answered 3런·budget-pressure 1런·연쇄 must-cite 누락이다 — 응답이 커지자 **예산을 말없이 넘기고**
(`rag-bp-change-flow` 0/2), 본문을 받고도 **마지막 홉을 인용하지 않았다**(`rag-chain-model-mismatch` 0/2,
`rag-stem-rules`, `rag-hop-stem-sides`, `rag-lit-stoplist`). 기본값은 지금처럼 id 응답으로 두고, `detail="full"`은
에이전트가 고르는 선택지로 남긴다.

**2. 설명 교체·이름 입력(B)은 방향이 맞지만 n=36에서 유의하지 않다.** 정답 +4런(84.7→90.3%, 6:2 p=0.29),
바이트 중앙값 동일. 기준 "+10%p"에는 못 미친다. 가장 큰 변화는 **채택**이다 — 옛 설명에서는 72런 중 27런이
graphin을 아예 안 썼고, 새 설명에서는 3런뿐이다. multi-hop이 14/18 → 18/18로 만점이 된 것이 정답 차이의
전부에 가깝다.

**3. B의 에이전트는 연쇄 응답을 스스로 골라 쓴다.** `detail="full"` 38회, `symbol` 입력 31회 — 기본값이
아니어도 설명만 보고 필요한 자리에서 불렀다. 강제(C)보다 선택(B)이 나았다.

### 판정 정정

**2런에서 본 B의 정답 우세는 잡음이었다.** 3런에서 두 팔은 같은 자리다(98 대 97). 2런에서 A가 잃었던
multi-hop(14/18)은 이번에 27/27이다 — 태스크당 2런으로는 한 런의 흔들림이 판정을 만든다. 이 저장소가
전에 적어 둔 교훈(2026-07-25 h1-reverify, 2026-09-08 36-grep)과 같은 모양이다.

남는 결론은 셋이다.

1. **새 설명은 정답률을 바꾸지 않고 도구 선택을 바꾼다.** graphin을 안 쓴 런 32 → 9, graphin 콜 +56%,
   호스트 콜 −19%. 두 측정(2런·3런)에서 같은 방향으로 재현됐다(27 → 3, 32 → 9).
2. **입력 오용이 절반으로 줄었다.** hybrid 키워드 나열 49% → 24%로 스펙 §5 기준("A 절반 이하")을 처음
   충족했다(2런에서는 46% → 28%). keyword 산문 1건(`"The response is a PREFIX"`)은 주석 문장을 그대로
   찾은 것이라 휴리스틱의 오탐이다.
3. **정답률이 같은 데서 바이트는 중앙값 +12%다(p=0.62, 유의하지 않음).** 에이전트가 `detail="full"`을
   70회 스스로 고른 값이다. 스펙 기준(+30% 이내) 안이다.

**연쇄 응답 기본값(C)을 두지 않는다는 판정 1은 그대로다** — C는 재측정하지 않았고, 2런에서 B보다 유의하게
낮았다(1:8, p=0.039). 2런의 잡음 폭을 감안하면 이 p도 보수적으로 읽어야 하지만, 방향(정답 하락·바이트 +40%)은
기본값을 바꿀 근거가 되지 못한다.

스펙 §5의 "정답 +10%p" 기준은 이 골든셋에서 닿을 수 없다 — A가 이미 90.7%라 천장까지 9.3%p뿐이다. 이
골든셋으로는 도구 계약의 값을 정답률이 아니라 **채택과 입력 모양**으로 재야 한다.
