# 키워드 검색기의 빈자리 넷 — 계측·기준선·결정론 측정 (2026-09-05)

[`docs/keyword-plan.md`](../../keyword-plan.md)의 1~3단계를 실행한 기록이다.
**이 디렉터리에 "개선"은 없다.** 있는 것은 (1) 이제 보이는 것, (2) 변경 전
기준선, (3) 제품 변경이 결정론 축에서 어떻게 보이는가, (4) 대조군이 움직이지
않았다는 확인이다. 개선 여부는 릴리스 뒤 rag 벤치를 다시 돌려 여기 적힌
기준선과 비교할 때 판단한다.

## 1. P4 — usage 계측이 키워드를 세기 시작했다

`search_keyword`는 출시(2026-08-31) 이후 `other`로 분류돼 채택·폴백·발견 실패
어느 지표에도 없었다. 이제 `g_search`이고, 리포트가 hybrid/keyword를 갈라 콜·런·
채택·폴백·same-intent·퍼널을 따로 낸다. 분류는 리포트 시점에 일어나므로 옛 로그에
소급된다.

이 저장소의 실사용 로그(4,233 이벤트)에는 여전히 `search_keyword`가 0건이라 이
표는 지금 비어 있다 — 그래서 절 자체가 keyword 콜이 0이면 렌더되지 않게 했다.
0으로 찍힌 행은 "채택 안 됨"으로 읽히기 때문이다.

같이 고친 것: same-intent 폴백 쌍이 키워드 런에도 붙는다(`pattern`을 쿼리로
읽는다). 퍼널은 어느 검색기의 id가 넘어갔는지로 나뉜다. usage-spec §4.1·§4.2·§4.3에
반영했고, 위키 `adoption` 세트의 세 항목은 요약이 그대로 맞아 repin했다.

## 2. M2 — 채점기 관찰 지표 (루브릭 1.3.1)와 그 첫 수치

관찰만 더했다(판정 불변): 키워드 콜 수, 결과 0건 수, 결과는 있는데 노드 id가 없는
응답 수, **키워드 뒤 3콜 안의 첫 소비 행동** 분포, 태스크의 첫 검색기.
`RUN_COMPAT`에 붙어 1.3.0 트랜스크립트를 재채점한다. 소유자 허가 → unlock →
수정 → `lock --approved-by salvia95` → unlock 삭제 순으로 진행했다.

리터럴형 태스크의 첫 검색기 비율은 **지금 잴 수 없다** — rag 태스크 27개 중
정확한 문자열을 인용한 질문이 하나도 없다. 첫 검색기 분포는 전체에 대해 낸다.
리터럴 태스크 신설은 골든셋 변경이라 이 계획 밖이다.

### 2.2 변경 전 기준선 (27태스크 × 3런)

두 번 돌렸고 둘 다 온전한 기준선이 아니다. 그 사정을 먼저 적는다.

- **첫 시도**: 변경 전 바이너리 + 변경 전 스킬(sha `e7b2b8…` = HEAD). 80/81에서
  사용량 한도(HTTP 429)로 중단 — 3런이 exit 1, 1런 미시작, **유효 77런**.
  스펙 §5대로 `summary.json`이 없어 채점기가 거부하므로 pass율은 기준선으로
  쓰지 않는다. 관찰 지표(콜 단위라 N에 의존하지 않는다)는 채점기 함수를 그대로
  불러 뽑았다. **이것이 진짜 변경 전이다.**
- **재실행**: 변경 전 바이너리인데 **스킬 본문은 P1 편집이 들어간 뒤의 것**이다
  (sha `5d8a9a…`). 편집 뒤에 다시 띄운 순서 실수다. 에이전트는 새 레시피를 읽고
  키워드 콜 317건 중 **226건에 `context`를 넘겼고**, 옛 바이너리는 그것을 오류
  없이 무시했다. 즉 "프롬프트만 바뀌고 도구는 안 바뀐" 상태이고, 변경 전
  기준선이 아니다. 대신 5단계(스킬 + 도구) 옆에 놓을 **프롬프트 단독 팔**로 쓴다.

깨끗한 81런(HEAD 스킬로 재실행)은 약 12달러와 한도 위험이 더 들어 소유자
결정으로 남긴다. 세 팔(변경 전 / 프롬프트만 / 프롬프트+도구)이 있으면 P1의
효과를 프롬프트 효과에서 가를 수 있다.

적어 둔 그 모양](../gate-log.md)이다. 행동은 맞고 표기가 틀린 것이며 골든셋
사안이라 여기서는 세기만 한다.

## 3. M1 — 결정론 축: 키워드 팔과 힌트 발화 (P1·P3 포함 빌드)

`scripts/eval-recall.py`에 두 가지를 더했다. 리터럴형 문항(`grep` 문자열이 있는
것)에 대해 `search_keyword`를 `context` 0·2·4로 부르는 **키워드 팔**, 그리고
모든 문항의 `search_hybrid` 응답에서 어떤 힌트가 떴는지의 **집계**. 골든셋
파일은 건드리지 않았다.

### 3.1 리터럴형 힌트는 산문 질의에서 뜨지 않았다

| 층 | 문항 | quoted | vocab | broad | 그 밖 |
|---|--:|--:|--:|--:|--:|
| base | 10 | 0 | 0 | 8 | 0 |
| variants | 4 | 0 | 0 | 4 | 0 |
| hop | 3 | 0 | 0 | 0 | 0 |
| tests | 6 | 0 | 0 | 5 | 0 |

새 규칙 둘(따옴표·어휘 부재)은 **23문항 중 0회**다. 계획서가 요구한 오발화
고정이 실제 인덱스 위에서 확인됐다. 부수 관찰: 기존 **"광범위" 힌트가 base
산문 질의의 8/10에서 뜬다.** 이 힌트도 "정확한 텍스트를 알면 search_keyword"라고
말하므로, 에이전트가 보는 유도 문구의 대부분은 새 규칙이 아니라 이 규칙에서
온다. 이 벤치에서 새로 잰 것이 아니라 전부터 그랬던 것이다.

### 3.2 키워드 팔 — 리터럴 3문항

| 문항 | ctx=0 | ctx=2 | ctx=4 | hybrid (참고) | grep 심볼 추측 |
|---|---|---|---|---|---|
| test-drop-assert | 100% · 719B | 100% · 1K | 100% · 2K | 100% · 5K | 100% · 10K |
| test-breadcrumb-assert | 100% · 457B | 100% · 575B | 100% · 790B | 100% · 4K | 100% · 6K |
| test-rename-drift-assert | 100% · 639B | 100% · 1K | 100% · 1K | 100% · 5K | 100% · 8K |
| **합** | **3/3 · 2K** | **3/3 · 3K** | **3/3 · 4K** | 3/3 · 14K | 3/3 · 24K |

- recall 3/3, delivery 3/3 — 모든 컨텍스트 폭에서. 계획서 M1 기준(recall 유지,
  ctx=2 delivery ≥ hybrid, 바이트 < grep의 절반)을 **넘는다**: 바이트는 hybrid 경로
  (search + read_code 3칸)의 1/5, grep 심볼 추측의 1/8이다.
- delivery가 ctx=0에서도 100%인 것은 이 층의 evidence가 곧 grep 문자열이라서다.
  컨텍스트의 값은 "주변 줄"에 있고 이 층은 그것을 채점하지 않는다 — **문항이
  주변 줄을 요구하지 않으므로 ctx의 효용은 여기서 재지지 않았다.** 그것은 행동
  축(파일 통째 Read가 줄어드는가)의 몫이다.
- 접힌 파일 0, id 없는 히트 0. 3문항은 정답이 전부 테스트 함수 안이다.
- **3문항이다.** 방향이지 판정이 아니다.

## 4. M3 — SWE-Explore grep 대조군 불변

P1이 `internal/keyword`에 필드를 더한 뒤 `--policy grep`으로 451개를 다시 냈다.
**451/451 제출이 원본(`out/grep-451`)과 라인 단위로 동일하고, 순서대로 합친
파일의 md5(`492471da…`)도 같다.** 매처와 정렬이 움직이지 않았으므로 [2026-09-04 종합](../2026-09-04-swe-explore-synthesis.md)
§2.1의 H3 수치(recall@300 30배, 제출 라인 2.2%)는 그대로 인용할 수 있다.

실행은 두 조각이다 — 첫 실행이 355/451에서 메모리 부족으로 죽었고(rag 기준선
런과 겹쳤다), 남은 96개를 필터한 벤치 파일로 따로 냈다. 결정론 정책이라 조각의
합은 한 번에 낸 것과 같다.
