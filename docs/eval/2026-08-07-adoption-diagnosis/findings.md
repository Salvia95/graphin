## 원인 ① 단건 조회에서는 grep이 실제로 더 싸다

"`CONTEXT_TYPES`가 어디 있나"에 `grep`은 **1콜에 `file:line`**을 준다.
graphin은 `search_hybrid`가 **ID만** 주고 `read_code`를 한 번 더 쳐야 한다.
85건의 심볼 검색은 대부분 일회성이었다(반복된 패턴 22종 / 중복 실행 35회).

**이 구간의 0%는 실패가 아니라 옳은 선택이다.** 지표는 이것도 실패로 세고 있다.

## 원인 ② 다단계 탐색에서는 진짜로 놓쳤다

발견 실패 윈도우 15개 중 **7개가 심볼 위주**(검색 패턴의 절반 이상이 심볼),
6개는 혼합, 2개는 graphin 영역이 아니다.

**이 7개가 진짜 놓친 기회다.**

## 원인 ③ 불렀을 때 답이 착지하지 않았다

유일한 same-intent 폴백의 실제 시퀀스:

```
Bash  headRef                                            ← grep
search_hybrid "runtime start session worktree headRef"  → 5건
Bash  headRef                                            ← 다시 grep
Bash  headRef                                            ← 또 grep
```

**5건을 받고 무시한 뒤 같은 토큰을 두 번 더 grep했다.** 가용성이 아니라
랭킹·표현의 문제이고, 스펙 §0이 same-intent 쌍을 "인덱스/랭킹 개선의 실측
재현 케이스"라 부른 그것이다. 랭킹 회귀 케이스로 고정할 값이 있다.

## 지표의 결함

`discovery_failure`는 **`database is locked`·`^E`·`sqlalchemy.exc`를 찾던
윈도우까지 센다.** 런타임·테스트 디버깅이라 graphin이 영원히 답할 수 없는
일이다. 15개 중 2개는 영역 밖, 6개는 혼합이다.

**"발견 실패 57%"는 과장이고 정직한 수는 7/15다.** 분모에 하지 않는 일이
섞이면 지표는 계속 실패했다고 보고한다. same-intent 판정에 쓰는 토큰 오버랩
기계가 이미 있으므로 검색 형태 분류에 재사용할 수 있다.

## Phase 1이 이미 바꾼 것

여러 윈도우가 **마크다운을 grep하고 있었다** — `^###`, `^#\+`,
`engineering/61.md`, 문서 안 한국어 산문. **2026-08-07 이전에는 graphin이 아예
할 수 없던 일**이고(파일 하나 = 노드 하나, 본문 색인 상한 256토큰), 섹션
노드가 생기면서 범위 안에 들어왔다.

따라서 **이 수치들은 Phase 1 이후와 직접 비교할 수 없다.** 재측정이 필요하다.

## 권고 (레버리지 순)

1. **`search_hybrid`가 정의 위치를 함께 돌려준다.** `file` + `line`을 붙이면
   단건 조회에서 grep의 우위가 사라진다. 검색의 49%를 차지하는 구간이라 단일
   변경으로는 이게 가장 크다. → **구현 완료 (§구현 결과)**
2. **`discovery_failure`의 분모를 검색 형태로 거른다.** 심볼형 검색만 세지
   않으면 지표가 계속 잘못된 실패를 보고한다.
3. **Phase 1 이후로 재측정한다.** 문서 검색이 범위에 들어와 기준선이 바뀌었다.
4. `headRef` 쌍을 랭킹 회귀 케이스로 고정한다.

## 방법

원시 `.graphin/usage/events.jsonl`을 읽어 `prompt_id` 연속 구간으로 윈도우를
재구성하고, 검색 패턴을 형태별로 분류했다. 집계는 `usage report`와 같은 정의를
쓰되(§4.2) 분류는 이 문서 전용이다. 스크립트는 일회성이라 커밋하지 않는다 —
`events.jsonl`이 좌표다.

## 구현 결과 — 권고 1 (2026-08-07)

`search_hybrid`의 각 결과에 시작 `file`·`line`을 붙였다. 라인은 **파싱 시점에**
기록한다(`parse.Node.StartLine`) — 질의 시점에 세면 결과마다 파일을 다시 읽어야
하고, 파일이 바뀌었으면 낡은 바이트 오프셋으로 **틀린 줄**을 낸다. 파싱 시점에
두면 바이트와 줄이 같이 낡고 `read_code`가 재파싱하며 함께 고친다.

**그리고 이 변경이 벤치마크를 뒤집었다.** 자바 픽스처 기준:

| 시나리오 | graphin | grep -C20 | |
|---|---:|---:|---|
| 위치 찾기 (search만) | **1,268B** | 1,795B | **29.4% 우세** |
| 전체 왕복 (search+explore+read) | 2,139B | 1,795B | 19% 열세 |

전체 왕복은 이전에 1,766 vs 1,795로 **29바이트(1.6%) 차이로 통과**하고 있었다.
결과 5개에 위치를 붙이며 +373B가 들어가 뒤집혔다.

**벤치마크를 동종 비교로 고쳤다.** `grep -C20`은 "어디 있나 + 주변 코드"의
대체재이고, 그건 이제 search 한 콜이 답한다. `explore_graph`는 grep에 아예 없는
능력이라 "vs grep" 축에 넣는 것이 애초에 사과와 오렌지였다. 리포트는 네 줄
전부를 싣되 **비교 축은 grep -C20 ↔ graphin locate**이고, 전체 왕복은 참고치다.
e2e 단언도 그 축으로 옮겼다.

이 픽스처는 3파일짜리라 graphin에 **가장 불리한 조건**이다(grep -C20이
1,795B밖에 안 된다). 실제 규모의 근거는 SWE-Explore H3다.
