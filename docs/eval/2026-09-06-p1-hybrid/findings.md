# D 팔 — 기제는 보이고 정답률은 움직이지 않았다. 사전 기준으로는 릴리스 보류 (2026-09-06)

P1 바이너리(`context`)·P3 힌트가 든 graphin 에이전트를 grep 대조군(C)과 프롬프트만
바꾼 팔(B) 옆에 놓는다. 27태스크 × 3런, sonnet, 코퍼스 `eae65b6`, 루브릭 1.3.3.
[manifest](manifest.md)에 적은 대로 하이브리드는 부분적이다(hybrid 응답 중 시맨틱 62%).

**결과: D 74/81 · B 73/81 · C 76/81.** 태스크 짝 비교 부호검정은 D 대 B가 3·2·22,
D 대 C가 3·4·20으로 **둘 다 p=1.0**. C와의 차이 중 3점은 소유자 유지 태스크
`rag-read-omission`이고 그것을 빼면 **D 74/78 대 C 73/78**. 정답률로는 세 팔이
구별되지 않는다 — [09-06 grep-control](../2026-09-06-grep-control/findings.md)과
[rescore](../2026-09-06-rescore-1.3.3/findings.md)의 결론 그대로다.

**P1의 기제는 보인다.** `context>0`을 넘긴 키워드 콜 209/283(74%), 창이 돌아온 응답
171. id 있는 히트 뒤 `read_code` 후속이 **21% → 10%**(47 → 22콜)로 반이 됐고,
키워드 콜 자체가 317 → 283(−11%), id 없는 히트 10% → 7%, 0건 21% → 19%.
**그러나 사전 기준(인수인계 §7-3)이 고른 두 지표는 움직이지 않았다**: 키워드 뒤
파일 통째 `Read` 8 → 9, 재검색 138 → 138(비중은 44% → 49%). 바이트는 중앙값
13.7K → 15.7K(+15%)로 올랐고 budget-pressure 층이 5/6 → 4/6이다.

## 3. 키워드 뒤 행동 — 조건부로 보면 무엇이 바뀌었나

키워드 콜 뒤 3콜 안의 첫 소비 행동을 **결과 종류별**로 나눈 것(`tools/kwnext.py`).

| 결과 | 팔 | n | 재검색(keyword) | hybrid | read_code(돌려준 id) | read_code(다른 id) | Read 통째 | explore | grep | 없음 |
|---|---|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| id 있음 | B | 218 | 37% | 18% | **21%** | 6% | 1% | 3% | 1% | 7% |
| id 있음 | **D** | 208 | **45%** | 16% | **10%** | 7% | 4% | 2% | 2% | 10% |
| ↳ 창 있음 | D | 171 | 48% | 12% | 9% | 9% | 4% | 2% | 2% | 11% |
| 0건 | B | 67 | 58% | 19% | — | 8% | 1% | 1% | 1% | 7% |
| 0건 | **D** | 55 | 52% | 14% | — | 9% | 0% | 7% | 5% | 9% |
| id 없음 | B | 32 | 56% | 6% | — | 15% | 9% | 3% | 0% | 9% |
| id 없음 | **D** | 20 | 70% | 5% | — | 15% | 0% | 0% | 0% | 10% |

- **창이 `read_code`를 대신했다.** id 있는 히트 뒤 돌려준 id를 읽는 콜이 47 → 22.
  이것이 P1이 설계한 효과이고, 실제로 났다.
- **그 자리를 재검색이 차지했다.** 같은 조건에서 재검색 37% → 45%. 창을 보고 "이
  히트가 아니다"를 더 빨리 판단해 다시 검색한 것인지(값싼 선별), 키워드 검색기를
  grep 루프처럼 돌린 것인지(인수인계 §1-4가 경계한 "래핑")는 이 지표로 안 갈린다.
  다음 질문은 여기다 — **창을 받고도 왜 다시 검색하나.** 0건 뒤 재검색은 P3b 힌트가
  시키는 행동이라 사전 기준 (b)의 "재검색 감소"는 P3b의 설계와 부분적으로 충돌한다.
- **"없음"이 늘었다**(7% → 10%): 키워드 결과가 마지막 소비 행동인 런 — 창만으로 답을
  쓴 경우가 포함된다. 방향은 맞다.
- **통째 Read는 창이 막지 못했다.** D의 통째 Read 9건은 전부 id 있는 히트 뒤이고 그중
  7건은 창이 있는 응답 뒤다 — 에이전트가 파일 전체를 원한 경우다. 81런에 9건(키워드
  후속의 3%)이라 P2(`read_code` 라인 범위)가 겨눌 표적으로는 작다.
- 힌트 순응 57% → 64%(56/98 → 54/85), 첫 검색기가 keyword인 런 11 → 19, 지어낸 id
  런 2 → 1. 예산 접힘(`omitted="budget"`) 8콜 — 캡이 실제로 발화했고 응답은 깨지지
  않았다.

## 4. 확립된 것

- **P1은 동작하고 설계한 자리에서 값을 낸다** — 히트 뒤 슬라이스 읽기 반감. 정답률과
  총 바이트로는 안 보이고 조건부 행동에서만 보인다. 이 골든셋이 잴 수 있는 것은
  그 정도다(질문이 어휘를 흘리고 코퍼스가 작다 — 09-06 grep-control §4).
- **세 팔은 정답률로 갈리지 않는다**(p=1.0 둘). graphin 대 grep의 값은 코드 연쇄
  질문(fk-edges)과 바이트(C 대비 17/27 태스크에서 적음)에 있고, 이 결론은 이제
  P1 바이너리·하이브리드-준비되면 팔에서도 같다.
- **rag 벤치의 `--semantic`은 부분 하이브리드다**(manifest). 하이브리드의 기여를 재려면
  러너/서버가 먼저 바뀌어야 한다.
- **budget-pressure는 응답 크기에 민감하다.** 창이 붙으면 20KB 가장자리에서 침묵
  초과가 난다. 고칠 자리는 캡이 아니라 "넘었다고 말하기" 규율(프롬프트)이다.

| (b) 키워드 뒤 통째 Read·재검색이 B보다 감소 | Read 8 → 9, 재검색 138 → 138(비중 ↑). 대신 `read_code` 후속 47 → 22 | **아니오** — 기준이 고른 두 지표는 안 움직였다 |
| (c) 회귀 없음 | budget-pressure 5/6 → 4/6(침묵 초과 2, 그중 하나 195B), 바이트 +15% | **불확실** — 편차 범위지만 방향이 나쁘다 |

**릴리스 보류.** 기준을 사후에 고쳐 통과시키지 않는다 — 그것이 이 저장소가 두 번
밟은 함정이다. 인수인계 §7-3의 "그렇지 않으면" 절대로 **P1은 opt-in(`context` 기본
0, 바이트 동일)으로 그대로 두고** 원인은 §2·§3에 적었다. 코드·스킬·채점기는 전부
테스트 통과 상태로 트리에 있고 커밋은 하지 않았다(§7).

**P2(`read_code` 라인 범위)는 지금 구현하지 않는다.** 통째 Read가 줄지 않은 것은
맞지만 81런에 9건이고, 창이 있어도 파일 전체를 원한 경우라 라인 범위가 대체할
행동이 아니다. 키워드 후속의 최대 항목은 재검색(49%)이고 P2는 그것을 건드리지 않는다.

## 6. 소유자에게 열린 것

1. **그래도 릴리스할 것인가.** 반론은 셋이다 — 기본값이 바이트 동일해 해가 없다,
   P4 계측은 실사용에서 키워드 채택을 재는 유일한 길인데 지금 로그는 `search_keyword`를
   `other`로 버린다(인수인계 §1-3), 기제는 실측됐다. 찬성하면 patch 0.4.12
   (`context`는 아무도 고칠 게 없는 새 기능, plugin-distribution §13.3) + 가이드 0.6.3.
   반대 논거는 §5 그대로다. **이 문서는 판단을 바꾸지 않는다; 기준을 바꾸는 것은
   소유자의 몫이다.**
2. **기준 (b)의 재검토** — "재검색 감소"는 P3b(0건 → 재검색 힌트)와 충돌하고, P1의
   실제 효과(`read_code` 후속 감소)는 기준에 없었다. 다음 재측정 전에 기준을 다시
   쓰려면 지금이다 — 데이터를 본 뒤라는 점을 적어 두고.
3. **깨끗한 하이브리드 팔** — 서버 준비 대기(제품) 또는 러너 워밍업. `RUN_COMPAT`
   리셋 여부 포함.
4. **budget-pressure의 침묵 초과** — 프롬프트의 "넘으면 말한다" 조항 강화는 agent_sha
   변경 = 재베이스라인.
