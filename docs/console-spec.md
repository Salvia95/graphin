# `graphin console` — 인수인계 (2026-08-21)

> **상태: 착수 안 함. 그리고 이건 "아직 못 했다"가 아니라 "지금은 짓지 않는 게 낫다고 판단했다"이다.**
> 이 문서는 다음 사람이 그 판단을 뒤집을지 정할 수 있도록, 판단의 근거와
> 짓기로 했을 때 즉시 걸리는 제약을 남긴다.

## 1. 왜 안 지었나

설계는 이렇게 잡혀 있었다 — 상주 서비스가 아니라 `graphin console` 서브커맨드,
localhost 서버를 띄우고(embed SPA + JSON API) 종료 시 소멸. 1차 범위는 읽기
전용 셋: **사용 통계 · 승격 큐 · 톰스톤 비율 게이지**.

착수 직전에 다시 보니 셋이 걸렸다.

**① 1차 범위가 이미 전부 커맨드로 나온다.**

| 화면 | 이미 있는 것 |
|---|---|
| 사용 통계 | `graphin usage report` |
| 승격 큐 | `graphin wiki queue` (대기 후보·미스·미열람 세트·낡은 핀을 한 화면에) |
| 게이지 | `diagnose_index`의 `<reverse … redirects="N">` + 20% 초과 시 힌트 |

세 번째는 이 세션에 넣었다(`0f53244`). 즉 콘솔이 주려던 값 중 **"한 화면에서
본다"만 남았고, 나머지는 이미 나온다.**

**② 대가가 영구적이다.** 이 저장소에는 지금 프런트엔드가 없다 — `package.json`도
`vite.config.*`도 없고, `go:embed`는 **단 한 곳도 쓰지 않는다**(확인함). React +
TS + Vite + Tailwind를 들이면 npm 의존성 트리, CI의 node 셋업, 릴리스 워크플로의
프런트엔드 빌드 단계, 그리고 `go:embed`가 먹을 산출물의 커밋 여부 결정이 **영구히**
따라온다. 지금 릴리스 워크플로는 `debian:bullseye` 컨테이너 안에서 `make build`
하나만 돈다(§5.2).

**③ 2026-08-14에 admin 페이지를 "진단만 남기고 화면을 버린다"며 전면 삭제했다.**
형태를 바꾼 복귀이므로, 그때 지운 이유가 아직 유효한지부터 답해야 한다.

## 2. 다시 볼 조건

아래 중 하나가 참이 되면 판단이 바뀐다. **아무것도 참이 아니면 짓지 않는 편이 낫다.**

- **여러 워크스페이스를 나란히 봐야 한다.** 커맨드는 한 저장소 안에서 돈다.
  프로젝트 5개의 채택률·큐를 비교하는 일이 생기면 커맨드로는 못 한다 — 이게
  콘솔이 유일하게 이길 수 있는 축이다.
- **비-CLI 사용자가 승격 큐를 리뷰해야 한다.** 지금 승인은 파일 이동이라
  git 다루는 사람만 할 수 있다.
- **시계열을 봐야 한다.** 마찰 로그·usage 로그에 시간축이 있는데 커맨드는
  스냅샷만 낸다. 추세가 결정에 쓰이기 시작하면 표로는 부족하다.

## 3. 먼저 알아야 할 제약 — 콘솔은 인덱스를 열 수 없다

**이게 설계 전체를 가른다.**

`graph.Open`이 리버스 델타 로그를 **여는 순간 truncate한다**
(`internal/graph/deltalog.go`). 그래서 MCP 서버가 워크스페이스를 쥐고 있는 동안
다른 프로세스가 인덱스를 열면 안 된다 — 진단이 CLI가 아니라 MCP 도구가 된 이유가
정확히 이것이고(`internal/mcp/tools/diagnose.go` 첫 주석), `graphin wiki`의
모든 verb가 인덱스 없이 도는 이유도 같다.

`graphin console`은 **별도 프로세스**다. 그러므로 같은 제약을 받는다.

1차 범위 셋을 이 축으로 재보면:

| 화면 | 데이터 출처 | 인덱스 |
|---|---|---|
| 사용 통계 | `.graphin/usage/events.jsonl` → `internal/usage` | **불필요** (확인함: `internal/usage`는 graph/workspace를 import하지 않는다) |
| 승격 큐 | `docs/wiki/**` + `.graphin/wiki/friction.jsonl` → `internal/wiki` | **불필요** (설계상 그렇게 만들었다) |
| 게이지 | `ws.GraphReverseStats()` → 엔진 | **필요** ← 문제는 여기 하나 |

**셋 중 둘은 그냥 된다. 세 번째만 답이 필요하다.** 선택지:

- **ⓐ 게이지를 1차 범위에서 뺀다.** `diagnose_index`가 이미 낸다. 가장 싸다.
- **ⓑ 서버가 안 떠 있을 때만 연다.** `.graphin/binpath`나 락으로 판별. 실패
  모드가 조용하고 사용자에게 설명하기 어렵다.
- **ⓒ 도는 MCP 서버에 붙는다.** 그러면 콘솔은 독립 도구가 아니라 MCP 클라이언트다.
  가장 정직하지만 stdio 전송에 두 번째 소비자를 붙이는 문제가 생긴다.

권고는 **ⓐ**다 — 1차 범위를 인덱스 무관으로 좁히면 콘솔은 순수하게 파일을 읽는
프로세스가 되고, 위 위험이 통째로 사라진다.

## 4. 스택 (설계 확정분, 뒤집으려면 근거가 필요)

**React + TypeScript + Vite + Tailwind + shadcn/ui**, `go:embed`로 단일 바이너리 유지.

기각된 것과 사유:
- **Go + htmx 지속** — 에이전트 생성 품질이 낮았다
- **SvelteKit** — 학습 분포가 얇다
- **Next.js** — 런타임 Node가 필요하고 SSR이 불필요하다

localhost 바인딩이므로 **인증·CORS는 생략**한다.

## 5. 규율 — API는 커맨드와 같은 함수의 얇은 껍질

설계가 못 박은 것: *API 핸들러는 CLI 커맨드와 동일 내부 함수의 얇은 껍질이고,
CLI JSON 출력과 API 응답 스키마를 공유한다(버전 있는 계약에 편입).*

**지금 코드는 그 준비가 반쯤 되어 있다.** 확인한 상태:

- `wiki.Summarize(ReadFriction(root)) → FrictionReport` — 값을 반환한다 ✅
- `Store.Queue() → []*Proposal` — 값을 반환한다 ✅
- `usage`의 `Report` 구조체가 있다 ✅
- **`runQueue(args, stdout, stderr) int`는 io.Writer에 직접 쓴다** ❌

그래서 첫 작업은 화면이 아니라 **표현과 데이터의 분리**다: `runQueue`가 데이터
구조를 만들고 렌더러가 텍스트를 찍도록 쪼갠다. 그 구조가 그대로 JSON 응답이 된다.
이걸 먼저 하면 콘솔을 안 짓기로 해도 손해가 아니다 — `--json` 플래그가 공짜로 생긴다.

## 6. 빌드·릴리스에 붙는 것

- `Makefile`에 프런트엔드 빌드 타깃(현재 타깃: `build` `vet` `test` `test-race` `fbs`)
- CI에 node 셋업. 지금 `ci.yml`은 Go + actionlint + shellcheck + 버전 불변식뿐이다
- 릴리스 워크플로의 build 잡이 `debian:bullseye` 컨테이너 안에서 도므로 **거기에
  node가 들어가야 한다** — glibc 하한(2.17, §10.3)에 영향이 없는지 확인 필요
- `go:embed`가 먹을 `dist/`를 **커밋할지 CI에서 빌드할지** 결정. 커밋하면 diff가
  더러워지고, 안 하면 `go build`만으로 빌드가 안 된다 — 지금은 된다
- `.gitignore`에 `/dist/`가 이미 있다(빌드 산출물용). 이름 충돌 주의

## 7. 버저닝

콘솔 추가는 §13.2의 다섯 표면 중 어느 것도 깨지 않는다(새 서브커맨드 = 추가).
§13.3에 따라 **patch**다. 릴리스 노트 프렐류드도 불필요하다 — 사용자가 손댈 게 없다.

## 8. 열린 질문

- **인증 없는 localhost 바인딩이 괜찮은가.** 설계는 괜찮다고 봤다. 다중 사용자
  머신이나 원격 개발 환경(devcontainer, Codespaces)에서는 재검토가 필요하다.
- **쓰기를 넣을 것인가.** 1차는 읽기 전용이지만 승격 승인은 자연스러운 다음
  후보다. 그런데 승인이 파일 이동인 이유는 **리뷰가 git diff이기 때문**이고,
  버튼으로 옮기면 그 성질이 사라진다. 쓰기를 넣으려면 이 교환을 먼저 정해야 한다.
- **`graphin wiki queue`를 확장하는 쪽이 더 나은가.** 콘솔의 실제 값이
  "한 화면"이라면, 그 화면을 터미널에 내는 비용은 함수 하나다. 콘솔을 짓기 전에
  이 대안을 먼저 배제해야 한다.

## 9. 짓기로 했다면 — 첫 조각

1. **표현/데이터 분리** (§5). 콘솔과 무관하게 값이 있고, 안 지어도 손해가 없다
2. `graphin wiki queue --json` · `graphin usage report --json`(이미 있음) 정합
3. `graphin console` 서브커맨드 — **인덱스를 열지 않는다.** 정적 파일 서빙 + 위
   두 JSON을 그대로 내는 핸들러 둘
4. Vite 스캐폴드 + `go:embed`. 이 단계에서 처음으로 되돌리기 어려워진다
5. 게이지는 ⓐ대로 범위 밖. 필요하면 `diagnose_index`를 보라고 링크만 건다
