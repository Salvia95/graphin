설계는 이렇게 잡혀 있었다 — 상주 서비스가 아니라 `graphin console` 서브커맨드,

| 화면 | 이미 있는 것 |
|---|---|
| 사용 통계 | `graphin usage report` |
| 승격 큐 | `graphin wiki queue` (대기 후보·미스·미열람 세트·낡은 핀을 한 화면에) |

## 2. 다시 볼 조건

아래 중 하나가 참이 되면 판단이 바뀐다. **아무것도 참이 아니면 짓지 않는 편이 낫다.**

- **여러 워크스페이스를 나란히 봐야 한다.** 커맨드는 한 저장소 안에서 돈다.
  프로젝트 5개의 채택률·큐를 비교하는 일이 생기면 커맨드로는 못 한다 — 이게
  콘솔이 유일하게 이길 수 있는 축이다.
- **비-CLI 사용자가 승격 큐를 리뷰해야 한다.** 지금 승인은 파일 이동이라
  git 다루는 사람만 할 수 있다.
- **시계열을 봐야 한다.** 마찰 로그·usage 로그에 시간축이 있는데 커맨드는
  스냅샷만 낸다. 추세가 결정에 쓰이기 시작하면 표로는 부족하다.

> **2026-08-22: 두 번째가 참이 됐다.**
>
> knowledge set은 사람의 승인이 **구조적으로** 필수다 — `wiki_propose`는 후보를
> 파일로 남길 뿐 절대 발행하지 않고, 승인은 사람이 파일을 옮기는 일이다. 그
> 필수 개입을 매번 터미널 텍스트로 읽고 손으로 처리하는 비용이, 위키를 실제로
> 키우는 것을 막는다.
>
> 조건은 "비-CLI 사용자"라고 적혀 있었지만 겨냥한 문제는 같다 — **승인이라는
> 피할 수 없는 개입에 붙은 마찰**이다. 조건을 좁게 읽어 "나는 CLI를 쓸 줄 아니까
> 해당 없음"으로 넘기면, 정작 그 마찰 때문에 큐가 비어 있는 상태를 "승인할 게
> 없다"로 오독하게 된다.
>
> 나머지 둘(여러 워크스페이스·시계열)은 **여전히 거짓이고, 짓는 근거가 아니다.**
> 범위를 넓힐 때 이 둘을 근거로 쓰려면 그때 다시 참인지 확인해야 한다.

> **2026-08-23: 세 번째(시계열)도 참으로 본다.** 위가 요구한 확인이다.
>
> 화면에 `Adoption` 타일이 생기면서 **막다른 길**이 하나 만들어졌다. 타일은
> 세션 레벨 채택(graphin을 쓴 세션 / 전체 세션)을 퍼센트로 내는데, 이 프로젝트의
> **헤드라인 채택률은 그 수가 아니다** — `usage-spec.md` §4.2의 채택률은
> 채택/(채택+폴백)이고 런 단위다. 이 저장소 실측으로 앞은 4/7(57%), 뒤는
> 2/13(15%)이다. 두 수가 같은 낱말을 달고 한쪽만 보이면, 화면이 조용히 틀린
> 답을 가르친다.
>
> 그래서 조건이 참이 된 방식이 **원래 적힌 것과 다르다.** §2가 상상한 것은
> "추세가 결정에 쓰이기 시작한다"였는데, 실제로 발화시킨 것은 **화면이 이미 그

> 다시 만든다.
>
> 범위는 **읽기 전용 리포트 한 화면**이다. 여러 워크스페이스 롤업은 여전히

## 3. 먼저 알아야 할 제약 — 콘솔은 인덱스를 열 수 없다

**이게 설계 전체를 가른다.**

`graph.Open`이 리버스 델타 로그를 **여는 순간 truncate한다**
(`internal/graph/deltalog.go`). 그래서 MCP 서버가 워크스페이스를 쥐고 있는 동안
다른 프로세스가 인덱스를 열면 안 된다 — 진단이 CLI가 아니라 MCP 도구가 된 이유가
정확히 이것이고(`internal/mcp/tools/diagnose.go` 첫 주석), `graphin wiki`의
모든 verb가 인덱스 없이 도는 이유도 같다.

`graphin console`은 **별도 프로세스**다. 그러므로 같은 제약을 받는다.

1차 범위 셋을 이 축으로 재보면:

| 화면 | 데이터 출처 | 인덱스 |
|---|---|---|
| 사용 통계 | `.graphin/usage/events.jsonl` → `internal/usage` | **불필요** (확인함: `internal/usage`는 graph/workspace를 import하지 않는다) |
| 승격 큐 | `docs/wiki/**` + `.graphin/wiki/friction.jsonl` → `internal/wiki` | **불필요** (설계상 그렇게 만들었다) |
| 게이지 | `ws.GraphReverseStats()` → 엔진 | **필요** ← 문제는 여기 하나 |

**셋 중 둘은 그냥 된다. 세 번째만 답이 필요하다.** 선택지:

- **ⓐ 게이지를 1차 범위에서 뺀다.** `diagnose_index`가 이미 낸다. 가장 싸다.
- **ⓑ 서버가 안 떠 있을 때만 연다.** `.graphin/binpath`나 락으로 판별. 실패
  모드가 조용하고 사용자에게 설명하기 어렵다.
- **ⓒ 도는 MCP 서버에 붙는다.** 그러면 콘솔은 독립 도구가 아니라 MCP 클라이언트다.
  가장 정직하지만 stdio 전송에 두 번째 소비자를 붙이는 문제가 생긴다.

권고는 **ⓐ**다 — 1차 범위를 인덱스 무관으로 좁히면 콘솔은 순수하게 파일을 읽는
프로세스가 되고, 위 위험이 통째로 사라진다.

## 4. 스택 (설계 확정분, 뒤집으려면 근거가 필요)

**React + TypeScript + Vite + Tailwind + shadcn/ui**, `go:embed`로 단일 바이너리 유지.

기각된 것과 사유:
- **Go + htmx 지속** — 에이전트 생성 품질이 낮았다
- **SvelteKit** — 학습 분포가 얇다
- **Next.js** — 런타임 Node가 필요하고 SSR이 불필요하다

스택을 옮긴 것은 취향이 아니라 **2026-08-14 admin 실패의 원인 진단**이다.
에이전트가 짜는 코드의 품질이 그 스택의 학습 데이터 두께를 따라간다면, 가장
두꺼운 쪽을 고르는 것이 화면을 다시 짓는 전제 조건이다. 기각 사유 세 줄이 전부
같은 축을 재고 있는 것도 그래서다.

**시각 언어는 `docs/design-system.md`에 있다.** 스택이 무엇인가와 그 스택으로 무엇을
그리는가는 다른 질문이고, 후자는 화면이 하나뿐인 지금도 근거 없이 흔들리기 가장 쉬운
쪽이다. 색·간격·타입·컴포넌트 규칙은 전부 거기 있고, 토큰의 구현은
`internal/console/ui/src/index.css`의 Tailwind `@theme` 블록이다. 지식 세트 `design`이
그 문서를 가리키므로 화면 작업을 시작하는 preflight가 알아서 물어온다.

localhost 바인딩이므로 **인증·CORS는 생략**한다.

## 5. 규율 — API는 커맨드와 같은 함수의 얇은 껍질

설계가 못 박은 것: *API 핸들러는 CLI 커맨드와 동일 내부 함수의 얇은 껍질이고,
CLI JSON 출력과 API 응답 스키마를 공유한다(버전 있는 계약에 편입).*

**지금 코드는 그 준비가 반쯤 되어 있다.** 확인한 상태:

- `wiki.Summarize(ReadFriction(root)) → FrictionReport` — 값을 반환한다 ✅
- `Store.Queue() → []*Proposal` — 값을 반환한다 ✅
- `usage`의 `Report` 구조체가 있다 ✅
- ~~**`runQueue(args, stdout, stderr) int`는 io.Writer에 직접 쓴다** ❌~~
  → **2026-08-22 해소.** `internal/wiki/queue.go`의 `QueueReport` +
  `BuildQueueReport(root)` + `RenderQueue(w, q, misses)`로 쪼갰고, `runQueue`는
  플래그와 마샬만 하는 껍질이 됐다. `wiki queue --json`이 함께 생겼다.

그 분리에서 정한 두 가지가 API 스키마의 성질을 결정한다.

- **절단은 렌더러에 있다.** `--misses N`은 터미널의 제약이고 `QueueReport`에는
  limit도 cursor도 없다 — 스크롤바가 있는 소비자는 전량을 받는다. 미스만 잘리고
  나머지 세 섹션은 안 잘린다: 다른 섹션을 조용히 자르면 목록이 짧아지는 게
  아니라 **일이 숨는다.**
- **빈 배열은 `null`이 아니라 `[]`다.** 빈 큐가 정상 상태이므로 콘솔이 가장 자주
  받는 페이로드이고, 거기서 `null.map()`은 "보여줄 게 없을 때 반드시 동작해야
  하는 화면"을 정확히 터뜨린다. `QueuedProposal.File`을 넣은 것도 같은 이유다 —
  승인이 그 파일을 옮기는 일이라, 이름만 있고 위치가 없으면 읽을 수는 있어도
  **처리할 수가 없다.**

## 6. 빌드·릴리스에 붙는 것

**2026-08-22에 전부 정해졌다.** 아래는 결정과 그 이유다.

- **`make ui`를 넣되 `build`의 선행 조건으로 걸지 않는다.** 이 저장소가 기여자에게
  요구하는 것은 Go 툴체인 하나뿐인데, 모든 빌드가 node를 요구하게 만들면 대부분이
  열지도 않을 서브커맨드 하나 때문에 그걸 판다. UI 없이 빌드된 바이너리는 런타임에
  그렇다고 말한다.
- **CI에 `ui` 잡을 넣었다.** `npm run build`가 `tsc`를 먼저 돌리므로 이게 타입
  검사이기도 하다 — 깨진 컴포넌트가 릴리스 때가 아니라 푸시 때 걸린다.
- **릴리스 컨테이너에는 node를 넣지 않았다.** build 잡이 `debian:bullseye`인 유일한
  이유가 glibc 2.31 하한인데, 거기에 node 툴체인을 들이면 그 컨테이너가 지키려던
  단 하나의 제약을 무관한 의존성 손에 맡기게 된다. 프런트엔드 산출물은 어느 libc가
  만들었는지 신경 쓰지 않으므로 **별도 잡에서 만들어 아티팩트로 건넨다.** 그래서
  glibc 하한 확인은 애초에 필요가 없어졌다.
- **`dist/`는 커밋하지 않는다.** 대신 `ui/dist/.gitkeep`을 커밋해 `//go:embed
  all:ui/dist`가 항상 해석되게 했다 — 패턴이 아무것도 매치하지 못하면 빌드가
  실패하기 때문이다. 그 결과 셋이 동시에 선다: **`go build` 단독 빌드가 살아 있고**,
  dist diff 소음이 없고, UI 없는 바이너리가 조용히 거짓말하지 않는다.
  릴리스는 빌드 직전에 `dist/index.html` 존재를 확인한다 — 없으면 자리표시가 실린
  채로 나가고 사용자가 열기 전까지 아무도 모른다.
- **`.gitignore`의 이름 충돌은 없었다.** 기존 `/dist/`는 루트 고정이라
  `internal/console/ui/dist/`를 잡지 않는다. 새 규칙을 따로 넣었다.

## 8. 열린 질문

- **인증 없는 localhost 바인딩이 괜찮은가.** 설계는 괜찮다고 봤다. 다중 사용자
  머신이나 원격 개발 환경(devcontainer, Codespaces)에서는 재검토가 필요하다.
- **쓰기를 넣을 것인가 — 넣는다. 경계는 워킹 트리다(2026-08-22 확정).**
  승인은 `docs/wiki/propose/<canonical>.md`를 `docs/wiki/glossary/`로 옮기는
  일이고 두 경로 모두 추적된다. 그러므로 "리뷰가 git diff"라는 성질을 죽이는
  것은 파일을 옮기는 행위가 아니라 **커밋하는 행위**다. 콘솔은 워킹 트리까지만
  쓰고 커밋하지 않는다 — 결과는 커밋되지 않은 변경으로 남고, 사람은 지금과
  똑같이 diff로 본다. 오히려 나아진다: 지금은 프런트매터를 손으로 짜야 하는데
  폼이 채우고, 검토 대상은 그대로 diff다.
  **이 경계를 넘기려는 요구(커밋·푸시·PR 생성)는 새 결정이지 확장이 아니다.**
- **`graphin wiki queue`를 확장하는 쪽이 더 나은가 — 아니다(2026-08-22 배제).**
  확장이 줄이는 것은 *읽는* 마찰뿐이다. §2에서 조건을 발화시킨 것은 *처리*의
  마찰 — 승인이 파일 이동이라는 사실 — 이고, 터미널에 무엇을 더 찍어도 그 이동은
  여전히 사람이 손으로 한다. 읽기만 필요했다면 `--json`으로 끝났을 것이다.

## 10. 갱신 — 화면이 자기가 시킨 일의 결과를 본다

카드 여덟 종이 전부 "에디터에서 고쳐라"로 끝난다. 그런데 콘솔은 파일을 한 번
읽고 다시 안 읽었다. **고치고 돌아오면 같은 카드가 그대로 있었다** — 화면을 두
번째부터 안 믿게 만드는 가장 빠른 길이다.

`GET /api/events`가 SSE로 "뭔가 움직였다"만 흘린다. **페이로드는 안 싣는다** —
JSON 엔드포인트가 이미 답하는 질문에 두 번째 답이 생기면 그게 §5가 막으려던 것이다.

**감시가 아니라 폴링이다.** `internal/watch`가 있고 잘 돌지만 그건 트리 전체에
재귀 OS 워치를 건다. 이 저장소에는 `internal/console/ui/node_modules`가 있고,
그런 트리에 재귀 inotify를 걸면 머신 전체의 사용자당 워치 한도를 태운다 — **정작
그게 필요한 MCP 서버의 워처까지** 같이 죽는다. 콘솔이 읽는 것은 작고 알려져 있다:
위키, 위키 엔트리가 가리키는 문서, 생성된 스킬, 마찰 로그. 누가 보고 있는 동안만
그 집합을 초당 한 번 stat하는 편이 더 싸고, 태울 한도가 없고, 프로세스가 죽어도
핸들이 안 남는다.

클라이언트는 SSE **와** window focus 둘 다 건다. 실패 방식이 다르기 때문이다 —
스트림은 창이 포커스를 잃지 않는 듀얼 모니터를 잡고, focus는 스트림이 아예 안
붙는 경우를 잡는다.

## 11. 결정이 끝날 수 있어야 한다 (2026-08-23)

`uncovered`만 **사람이 끝낼 수 없는 종류**였다. 나머지 일곱은 현재 상태에서
파생되므로 고치면 사라지는데, 이것만 append-only 로그에서 파생됐다. 세트를 써도
과거 miss 이벤트는 남고, 카드가 사라지는 건 로그가 **용량으로 회전될 때뿐**이었다
(`internal/wiki/friction.go`).

이제 `BuildOverview`가 각 miss에 대해 **그 miss가 기록될 때 쓰인 것과 같은
술어**(`Store.Select(role, task).Empty()`)를 다시 묻는다. 지금 매치되면 결정이
아니다. 소급 스윕이 아니다 — 새로 발견하는 게 없고, 조건이 끝난 결정을 물릴 뿐이다.

**남는 긴장 하나를 적어 둔다.** role 푸시는 무조건이라, 넓은 세트 하나에
`roles: [ops]`를 달면 그 role의 miss가 **전부** 물러간다. 그게 술어 자체의
성질이고(그 에이전트가 다시 물으면 실제로 세트를 받는다), 콘솔이 여기서 다른 답을
내면 §5가 막으려는 "한 질문에 두 답"이 된다. 그래서 고치지 않고 **보이게** 했다 —
`Health.Answered`가 물러간 수를 세고 백로그 탭이 그걸 말한다. 조용히 줄어드는
숫자는 두 번 못 믿는다.

## 12. repin의 범위 (2026-08-23)

드리프트 카드는 "그 절을 다시 읽고, 그 요약이 아직 맞는지 확인하고, repin하라"고
말하는데 버튼은 `RepinAll` 하나였다. 둘이 드리프트했을 때 하나만 확인하고 누르면
**나머지도 조용히 축복된다** — 핀의 목적과 정반대이고, 그것도 경고를 지우는
방식으로 그렇게 한다.

`wiki.RepinEntry(root, set, node)`가 하나만 갱신한다. `POST /api/wiki/repin`은
본문이 비면 전부, `{set, node_id}`면 하나다. 반쪽 쌍은 400 — 어느 쪽을 뜻했는지
추측하면 안 읽은 엔트리를 보증하거나 아무것도 안 하게 된다. 그 세트가 실제로
그 노드를 나열해야 한다(404): 아무 문서도 뒷받침하지 않는 핀이 lockfile에
남으면 다음 `RepinAll`까지 거짓을 주장한다.

`Repin all`은 남아 있지만 **그룹 헤더**로 갔고, 드리프트가 둘 이상일 때만 뜬다.
"아래를 다 읽은 사람"의 컨트롤이지 카드의 컨트롤이 아니다.
